# binary_opc.sh bare-return swallows opc_cmd.sh generation failure

## The swallow (engineering-chain defect)
`scripts/kernel/binary_script/build_binary_opc.sh:52` (identical in ops-nn and omni-ops) used a **bare `return`** after printing the gen_task error:
```bash
local gen_res=$?       # gen_task exit code captured
if [ $gen_res -ne 0 ]; then
  echo -e "[ERROR] ..."
  return               # bare -> returns $? of the PRECEDING echo = 0
fi
```
A bare `return` returns the exit status of the last command run before it, which is the `echo -e` (success=0). So `main` returns 0, `set -o pipefail; main "$@"` exits the script 0, the `config_compile_*` cmake custom target reports success even though opc_cmd.sh was NOT written.

**omni-ops fixed** (2026-08-04): `return ${gen_res}` propagates the real exit. **ops-nn still has the bare return** (not touched, out of scope).

## What opc_cmd.sh is and who generates it
- File: `${BUILD_PATH}/binary/<unit>/bin/opc_cmd/opc_cmd.sh`, one `asc_opc ...` line per kernel variant.
- Generator chain: cmake `prepare_binary_compile_<unit>` → `config_compile_<op>_<unit>` (gen_binary_from_json.cmake:130, COMMAND = `build_binary_opc.sh`) → `build_binary_opc_gen_task.sh:355` does `echo ${cmd} >> opc_cmd.sh` inside the impl_mode×threadnum loop.
- The structure IS wired into prepare (gen_binary_from_json.cmake:149 `add_dependencies(prepare_binary_compile_${unit} config_compile_${unit}_${op} ${CONFCMP_TARGET})`). It is NOT a wiring gap. Confirmed by reading the file.

## The real runtime cause of empty opc_cmd.sh (V4 case)
`build_binary_opc_gen_task.sh:151-156` greps the op in `${topdir}/build/tbe/temp/_<soc>_tmp.csv`. If the op is absent → `exit 2`. The CSV is produced by `build_binary_gen_opc_info.sh` → `gen_opcinfo_for_socversion.sh` → `gen_opinfo_json_from_ini.sh` parsing the merged ini `${ASCEND_KERNEL_CONF_DST}/aic-<soc>-ops-info.ini` (merged by `merge_ini_files_for_binary` from autogen/{,inner/,exc/} inis generated by `opbuild_gen_*` via op_host_aclnn proto compiler).

So empty opc_cmd.sh = the op did NOT get an entry in the autogen ini (op_def/proto not in scope of op_host_aclnn build, or wrong op_type field in binary.json). That is the upstream root to chase, not the wiring.

## Why OPC_NUM ends up = 1 (the 1-variant symptom)
- build.sh:204 counts opc_cmd.sh lines = 0 (file absent after gen_task exit 2).
- build.sh:209 `-DOPC_NUM_<unit>=0`.
- CMakeCache shows `OPC_NUM_<unit>:UNINITIALIZED=0` (command-line -D value).
- gen_binary_from_json.cmake:172-175 `if(NOT ${OPC_NUM_UNIT})` → 0 is false-y → `set(... 1)`.
- compile_from_config foreach(idx RANGE 1 1) → only `exe_compile_<unit>_1` shard → only json_0 variant compiled.

## Defense added in omni-ops (2026-08-04)
- build_binary_opc.sh: `return ${gen_res}` (propagate).
- build.sh:205-208: after prepare, if `opc_list_num == 0` → explicit `log ... ; exit 1` instead of silently continuing to OPC_NUM=0.

## How to verify on server (when empty recurs)
1. `cat ${BUILD_PATH}/build/tbe/temp/_ascend910b_tmp.csv | grep <op_type>` — empty = op not registered in ini.
2. `grep <op_type> ${BUILD_PATH}/autogen/aic-ascend910b-ops-info.ini` (+ inner/, exc/) — confirm op_def/proto build scope.
3. `cmake --build ${BUILD_PATH} --target prepare_binary_compile_ascend910b -- -j 1 -v` → see `build_binary_opc_gen_task.sh` exit code now propagated (no longer 0).
