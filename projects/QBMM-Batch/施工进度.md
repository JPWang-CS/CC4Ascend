`aclnn_quant_matmul_v5.cpp` 内的 `CheckScaleX1Shape`（L588）/ `CheckScaleX2Shape`（L625）是硬编码 MX scale 3 维校验，但它们**仅被 A8W4 专用路径** `CheckParamsA8W4Float` / `CheckParamsA8W4Int` 调用。MX FP8×FP8 走的是 `CheckDimRange`（DAV_3510 跳过 x2Scale dim 检查）+ 共享 `QuantMatmulChecker::CheckParams()`，**不经过** `CheckScaleX1Shape`/`CheckScaleX2Shape`；而 A8W4 路径 x1/x2 强制 2D、无 batch。

## 6 实现注意事项（坑点 + 落地前 checklist）

整理 diff 时发现的易错点，落地各改动点前逐条核对，避免返工。

### 6.1 #5 kernel：scale/pertokenScale 偏移绝对不能带 `>> sizeShift`（高优先级坑）

`AddBatchOffset` 里 a/b 指针偏移带 `>> sizeShift`（`IsFp4<AType>() ? 1 : 0`），是因为 **FP4 把两个元素打包进 1 字节**，元素数右移 1 位才是字节偏移。

但补 scale/pertokenScale 偏移时**绝对不能复制这个右移**：

- scale/pertokenScale 是 `fp8_e8m0_t`，**每元素 1 字节、不打包**，元素数即字节偏移。
- 误加 `>> sizeShift` 后，FP4 场景下 scale 偏移会**减半**，从第 2 个 batch 起读到错位的 scale 数据（FP8 场景 sizeShift=0 不受影响，更隐蔽）。

因此 2.6.5 的两行偏移**保持无位移**：`pertokenScaleGmAddr_ += batchAOffset_ * (M * ceil(K/64) * 2)`，`scaleGmAddr_ += batchBOffset_ * (N * ceil(K/64) * 2)`。建议代码注释里点明"scale 为 e8m0 每元素 1 字节，不可右移，与 a/b 的 FP4 打包不同"。

### 6.2 落地前 checklist

- **#1（aclnn gate）上服务器前**：grep `CheckDimRange(` 的所有调用点，确认 x1Scale（pertokenScale）确实走放开后的 `<4` 路径，别遗漏某个入口仍走旧逻辑。
- **#3 / #4（CheckInputValidInMxPerGroupMode）参数顺序**：`.h` 声明、`.cpp` 定义、L982 调用点三处必须统一为 `(x1Shape, x2Shape, scaleShape, pertokenShape, dimValueOfMKN)`，三处不一致会编译失败或传参错位。

## 6.5 部署坑：custom 包必须装进 toolkit opp 标准 vendors（2026-06-17 实证，重装环境必看）

**现象**：自编 ops-nn 装成 custom 包、`ASCEND_CUSTOM_OPP_PATH` 指向**工程目录**（`/home/.../qbmm-batch/vendors/custom_nn`）后，跑 `QuantBatchMatmulV3` 首个 MX 用例报 `561103 / Tiling parse ctx is NULL / tiling compile info parse failed`，其余用例跑固定垃圾值（`-6645092/415318`）。清空 `ASCEND_CUSTOM_OPP_PATH=""` 回落 builtin → 全 PASS。**与 #1/#2 代码、ops-tensor 全无关，是纯部署问题。**

**根因（plog 实证）**：custom 的 host tiling-parse（`libcust_opmaster_rt2.0.so`）在运行期硬依赖 builtin 的 `libophost_comm_legacy.so`，靠 `legacy_common_manager.cpp` 的 `GetSoPathForCustomOp`（L143-166）做 **10 层 `../` 相对回溯**去找它。该回溯**假定 custom 的 `vendors/` 与 toolkit 的 `built-in/` 在同一个 opp 根下**。custom 挂在工程目录时，回溯算出 `/home/.../qbmm-batch/opp/built-in/.../libophost_comm_legacy.so`（不存在）→ `Fail to get` → parse ctx NULL → 561103。

plog 铁证（`ASCEND_GLOBAL_LOG_LEVEL=0`）：
- `legacy_common_manager.cpp:159 GetSoPathForCustomOp try to find ... /qbmm-batch/.../op_tiling/lib/linux/aarch64/../*10/opp/built-in/.../libophost_comm_legacy.so`（落到工程目录、不存在）
- `legacy_common_manager.cpp:75 GetLegacyCommonSoPath Fail to get libophost_comm_legacy.so path.`
- 对照：builtin 的 `libophost_nn.so` 走 `GetSoPathForBuiltin`，legacy so 同目录、零回溯，永远命中 → 清空 custom 全过。

**解法**：custom 包装进 toolkit opp 标准 vendors（`$ASCEND_TOOLKIT_HOME/opp/vendors/custom_nn`），即默认安装位置，使 10 层回溯落到同 opp 根下真实存在的 builtin legacy so。`build.sh` 用默认安装（不要手动把包丢进工程目录再用 `ASCEND_CUSTOM_OPP_PATH` 指过去）。

**附带坑（同一病根）**：plog 还暴露 custom 包 `liboptiling.so` 放在 `op_tiling/` 而非规范的 `op_tiling/lib/linux/aarch64/`（`op_tiling_manager.cc` dlopen 标准路径失败、退到上级才成功），`op_master/lib/linux/aarch64/` 也缺。说明手动摆放的 custom 布局整体非标准；默认安装会一并摆正。

**重装环境 checklist**：①custom 包走 `build.sh` 默认安装、落到 toolkit opp 的 `vendors/`；②`env | grep ASC` 确认 `ASCEND_CUSTOM_OPP_PATH` 指向标准 vendors 或 unset 走自动扫描；③先跑 `golden_mx_matmul.py` 无 batch 基线确认部署正常（全 PASS）再做 batch 实验。

### 7.2 阶段二 — ops-tensor Blaze kernel（#5）

落地范围：改动点 #5 `include/blaze/gemm/kernel/kernel_qbmm_mx.h` `AddBatchOffset`（L345-377）补两行 batch 偏移：
- `pertokenScaleGmAddr_ += batchAOffset_ * (M * ceil(K/64) * 2)`
- `scaleGmAddr_ += batchBOffset_ * (N * ceil(K/64) * 2)`
- **绝不带 `>> sizeShift`**（见 6.1：scale 为 e8m0 每元素 1 字节、不打包；误右移会让 fp4 场景偏移减半）。

编译：改完编 ops-tensor + 重编 ops-nn（ops-nn 拉的是 ops-tensor 头，必须连带重编）。

- fp8 多 batch：`1b_fp8_basic`、`1b_fp8_B8`（8 batch 放大偏移错位）、`2b_fp8_basic`、broadcast `bcast_A_fp8`/`bcast_B_fp8`。
- **fp4 关键**：`3b_fp4_chk5`（3 batch + fp4，专为暴露 #5 的"scale 偏移漏写 + 不可右移"双坑设计）、`1b_fp4_basic`。

## 9 FP4 transposeX2=false 设计（2026-06-18，决定二）

研究结论 + 设计方案见 `实施方案.md` 第 4 章。要点：
- 根因：fp4 的 ×2 翻倍发生在**最内层存储维**（op-plugin `QuantMatmulKernelNpuOpApi.cpp` L207-212、meta `_meta_registrations.py` L3650-3651 实证）。当前 int8-passthrough 未做最内层 /2 打包，故只有 trans_x2=true（K 落在 x2 最内层、与 x1 同步 ×2）能对齐；trans_x2=false 时 x2 最内层是 N、K 不翻倍 → K=512≠256。
- 当前模型**不可达** transposeX2=false，缺的是数据构造侧真正的 2:1 打包（x2 存 `(K, ceil(N/2))`）。
- 设计方案：加 `pack_fp4_lastdim` 辅助 + 按 trans_x2 决定打包维 + 调整 `x2_stored_transposed` 闸门（分支隔离，不破坏现有 fp4 trans_x2=true 路径）。
- 风险：nibble 打包序与 e2m1 LUT repo 无源（小整数 passthrough 可绕，真值对数须上板）；内轴偶数 vs n>2 交互使最小正向 N=4。
- 决定二仅出方案，**不改 golden 实现**，等用户确认。

### 12.2 groupSize 修复（fp8 NZ 根因，关键 bug）

**bug**：`call_npu` 传 `group_sizes=[0,0,32]`，但 MX 文档要求 `[1,1,32]`（aclnn 文档 L573 groupSize=4295032864 解码 [1,1,32]）。
- V5(ND) tiling 把 M/N=0 **推断成 1**（正确）→ ND 路径无感，原 17 例 PASS
- WeightNz(NZ) tiling 把 M/N=0 **推断成 32** → `[32,32,32]`：1b 被 MX 校验拒绝（561103 EZ0027）；2b/3b tiling 放过但用错 groupSize（每 32 行共享 scale vs golden 每行独立）→ 数值严重错位 cos≈0.04

### 12.3 fp4 NZ 在 torch 层不可达（查仓确认，2026-06-26）— ⚠️ 结论作废, 见 §12.5

fp4 NZ 经两轮尝试（fp32 中转 `.to(fp4)` on NZ / on ND）均失败。查仓定位根因：**仓里所有 fp4 NZ 处理都是 aclnn C 层 `aclnnCast`**（`examples/arch35/test_..._mxfp4.cpp:217`、`f8mxf4.cpp:247`、`a8w4.cpp:223`、`docs/...WeightNz.md:1451`），**torch 层（op-plugin）零先例**。

三重障碍致 torch `npu_quant_matmul` 路径走不通：
1. **`torch.to(float4_e2m1fn_x2)` device error 107001**（devId 40 非法，ND/NZ 都炸，底层 bug）—— 无法 fp32→fp4 cast，仓里别人全靠 aclnnCast 绕开
2. **op-plugin `transpose2` 恒 false**（QuantMatmulKernelNpuOpApi.cpp:235），但 fp4 打包沿 K（x2 转置朝向），NZ 需匹配 transposeX2=true
3. **MX 量化沿 K** + **fp4 打包沿 K**（x2_stored_transposed 设计），改 NZ 非转置朝向会破坏量化轴

**结论**：fp4 NZ 须走 aclnn C 直调（aclnnCast），torch npu_quant_matmul 当前不支持。非 golden 能解决，属 op-plugin/torch_npu 能力缺口。fp8 NZ（3 例）已覆盖 WeightNz 核心路径，fp4 NZ 不阻塞，留待算子/plugin 侧补能力。

### 12.5 fp4 NZ 修复（cast→transpose 顺序，2026-06-27）

fp4 NZ 初试失败（transpose not same / device error）。参考官方测试 `D:/Desktop/TMP/tmp.py` L641-648 定位根因：**cast→transpose 顺序**。

- **错顺序**（原）：`transpose → .contiguous() → npu_format_cast` —— `.contiguous()` 抹掉 transpose 的 stride 转置 → `is_x_scale_same_transpose` 判 x2/scale 不一致

- 修复后 fp4 NZ（1b/3b）PASS，且 fp8 NZ（已 PASS）不受影响（fp8 非 x2_stored_transposed，cast 前/后等价）

> 之前的"fp4 NZ torch 层不可达"结论（§12.3 旧版）**作废** —— 实际可走通，是顺序错。
