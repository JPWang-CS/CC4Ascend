# MX Scale Batch 支持 — 设计文档（精简版）

> 本文为纯设计文档，省略所有代码片段与行号级定位，仅保留设计目标、架构、关键决策与理由。完整实现细节见 `实施方案.md`。

# 1 算子需求

## 1.1 设计约束

- 运行环境：A5（Ascend 950），MX kernel 走 Blaze（CANN≥9.1）或 CMCT（CANN 9.0）路径
- 调用方式：单算子 `aclnnQuantMatmulWeightNz`
- 适用算子：`quantBatchMatmulV3`，MX 全量化路径
- 设计原则：简洁、最小改动
- 涉及仓：
  - `ops-nn`（算子实现，校验层）
  - `ops-tensor`（Blaze TensorAPI 库，kernel 层）
  - `op-plugin`（torch 适配层）

## 1.2 需求描述

### 1.2.1 功能描述

MX 全量化场景下，为 scaleX1（pertokenScale）与 scaleX2（scale）增加 batch 维度支持。变更前 scale 为固定 3 维，变更后允许在前面附加与 x1/x2 一致的 batch 前缀：

| | 变更前 | 变更后 |
|---|--------|--------|
| scaleX1 shape | `(m, ceil(K/64), 2)` | `(batchA, m, ceil(K/64), 2)` |
| scaleX2 shape | `(ceil(K/64), n, 2)` | `(batchB, ceil(K/64), n, 2)` |

batch 维度数与 x1/x2 的 batch 维度数一致，且各维值需逐维匹配。

**转置布局（最终设计目标，与官网 `aclnnQuantMatmulWeightNz.md` 对齐）：** scale 前两维跟随对应输入的转置，最后一维固定为 2。固定 3 维部分四组合如下（实际使用时在最前强制附加 batch 前缀）：

| tensor | transpose=false | transpose=true |
|--------|-----------------|----------------|
| scaleX1（pertoken_scale） | `(m, ceil(k/64), 2)` | `(ceil(k/64), m, 2)` |
| scaleX2（scale） | `(ceil(k/64), n, 2)` | `(n, ceil(k/64), 2)` |

约束：x1 与 scaleX1、x2 与 scaleX2 的转置属性必须保持一致。因此 M/N/K 维索引随转置切换（见 2.4 `CheckDimValueMicroScaling` 的 `batchDimNum + (transpose ? .. : ..)` 公式），batch 前缀始终在最前、不受转置影响。

### 1.2.2 适用范围

仅 MX 全量化场景涉及（x1/x2 dtype 为 F8_E4M3FN / F8_E5M2 / F4_E2M1，scale dtype 为 F8_E8M0，x1/x2 维度 3-6D）。MX 全量化强制带 batch：x1/x2 必须 ≥ 3D（含 ≥1 层 batch），scale 对应附加 batch 前缀（scale dim ≥ 4）。x1/x2 为 2D（无 batch）不再支持，接口层直接拒绝。

MX A8W4 场景（x1 强制 2D）不在本次范围内。

### 1.2.3 精度要求

精度继承原算子 MX 量化标准，满足 mxfp8/mxfp4 精度验收标准。

# 2 算子设计

## 2.1 总体设计

### 2.1.1 核心思想

将 scale 的维度模型从固定 3 维改造为 `batchPrefix + MX固定3维`：

```
Scale Shape:  [batch_0, ..., batch_N] + [M或ceil(K/64), ceil(K/64)或N, 2]
               ← batchDimNum →           ← MX 固定 3 维 →
               batchDimNum = totalDimNum - 3
```

所有访问 M/K/N/Last 维度的索引统一改写为 `batchDimNum + offset`（`batchDimNum = totalDimNum - 3`，减去 MX 固定 3 维）。接口层强制带 batch，`batchDimNum ≥ 1`，索引在固定 3 维基础上整体前移 batch 层数。

### 2.1.2 与 GMM 的 batch 差异

需要与 GMM（grouped_matmul）的 batch 概念区分，二者本质不同：

| | GMM | QBMM V3 |
|---|------|------|
| batch 本质 | experts 分组，每组 M/N/K 不同 | MatMul 批量，所有 batch 共享 M/N/K |
| x 维度 | 始终 2D `(M, K)` | 3-6D `(batch, M, K)` |
| scale batch 来源 | groupList（experts 个数） | x1/x2 的 batch 维 |
| tiling | 按组独立计算 | 统一，batch 仅作计算量乘数 |
| 需新增 tiling 字段 | 不需要（复用 groupList） | 不需要（复用 batchA1-4 / batchB1-4） |

关键结论：QBMM V3 的 scale batch 信息在 tiling 结构 `QuantBatchMatmulV3BasicAPIDataParams` 中已经以 `batchA1-4` / `batchB1-4` 形式存在，kernel 层可直接复用现有 batch 维计算 scale stride，无需新增任何 tiling 字段。这是本设计能做到"最小改动"的核心原因。

### 2.1.3 A5 调用链与路径分析

A5（DAV_3510）torch 层按 x2 格式路由：x2=ND 走 `aclnnQuantMatmulV5`，x2=NZ 走 `aclnnQuantMatmulWeightNz`。两条路径最终都汇聚到 `l0op::QuantBatchMatmulV3()`，共享同一套 checker / tiling / kernel。

为什么 V5 路径不涉及改动：V5 自己的 `CheckDimRange` 在 A5 上已经跳过了 x2Scale 的 dim 检查，因此 ND 路径天然放行高维 scale，无需修改。需要改的是 WeightNz 入口（NZ 路径）的 `CheckDimRange` gate，以及两条路径共享的 checker 与 kernel。

需要改动的逻辑节点（按数据流顺序）：
- 共享 checker `QuantMatmulChecker::CheckParams()`：`CheckMxScaleDimRange`（维度数严格相等校验）、`CheckDimValueMicroScaling`（硬编码索引）、`InferGroupSizeM/K/N`（硬编码索引）
- V3 tiling checker：`MxPertokenScaleShapeCheck`、`MxScaleShapeCheck`（均为维度数严格相等 + 硬编码索引）
- V3 kernel（ops-tensor）：`AddBatchOffset` 缺少 scale 指针的 batch 偏移

补充说明：`aclnn_quant_matmul_v4.cpp` 文件名中的 "v4" 是 aclnn API 版本号，该文件同时承载 V3/V4/WeightNz 三个入口，MX FP8×FP8 最终调用的是 V3 算子。

不在范围内：MX FP8×FP4（A8W4）的 x1/x2 强制为 2D，不在本特性范围内，不需要改动。

### 2.1.4 IS_BLAZE 路径约束（双路径对称）

MX（E8M0 scale）的 kernel 路径由编译期宏 `IS_BLAZE` 选择，两条路径都需要对称补 scale batch 偏移：

- `IS_BLAZE` 仅由 CANN/asc-devkit 版本决定：条件为 `ASC_DEVKIT_MAJOR>=9 && ASC_DEVKIT_MINOR>0`，即 CANN≥9.1 时为 true 走 Blaze 路径；CANN 9.0.0（MINOR==0）下为 false 走 CMCT 路径。全仓不存在 build.sh 或命令行开关可以覆盖该宏，无法手动强制切换。
- 该宏决定 MX 走哪条 kernel：true → Blaze 路径（wrapper `qbmm_mx_tensor_api_blaze.h`，实现在 ops-tensor 的 `blaze/gemm/kernel/kernel_qbmm_mx.h`）；false → CMCT 路径（wrapper `qbmm_mx_basic_api_cmct.h`，实现在 ops-nn 的 `matmul/common/cmct/kernel/kernel_qbmm_mx.h`）。代码证明（`quant_batch_matmul_v3.cpp` L16-20、L37-44）：`#if ASC_DEVKIT_MAJOR>=9 && ASC_DEVKIT_MINOR>0` → `IS_BLAZE true`，否则 `false`；随后 `#if (ORIG_DTYPE_SCALE==DT_FLOAT8_E8M0)&&IS_BLAZE` 拉 Blaze 头，`#elif (...==DT_FLOAT8_E8M0)` 拉 CMCT 头。即 CANN 9.0.0（MINOR==0）的 E8M0 场景必走 CMCT。完整片段见实施方案 2.6.1。
- **batch scale 同时支持两条路径**：本设计的 kernel scale batch 偏移改动（见改动点 5/5b）在 Blaze 与 CMCT 两份 `AddBatchOffset` 中**对称落地**，公式完全相同（pertokenScale=M×ceil(K/64)×2、scale=N×ceil(K/64)×2）。CANN 9.0（CMCT）改 #5b、CANN≥9.1（Blaze）改 #5，**fp8/fp4 在两条路径下均支持**。两份偏移逻辑必须保持同步，任一份漂移会静默读错 scale、不报编译错。
- 旧表述更正：早期"kernel 改动只落在 Blaze、CANN 9.0 不支持 / fp4 仅某一路径可用"的说法不成立。batch scale 与 fp8/fp4 在 9.0(CMCT) 和 9.1(Blaze) 两条路径都支持。9.0.0 CMCT 的 fp4 LoadData 既有缺陷是独立于 scale 偏移的问题，本设计不触碰。

路径选择结论：编译与验证服务器可在 CANN 9.0（CMCT）或 ≥9.1（Blaze）任一环境落地，只需保证对应路径的 `AddBatchOffset` 已补 scale 偏移；两条路径的 host 侧（改动点 1-4）完全复用，路径无关。

### 2.1.5 改动点全景

共 7 个改动点（kernel 双路径对称），分布在 3 个仓：

| # | 仓 | 文件 | 改动本质 |
|---|-----|------|---------|
| 1 | op-plugin | `ops/opapi/QuantMatmulKernelNpuOpApi.cpp` | transpose 校验中 MX 分支的 scale dim 从固定 0 改为 `dim()-3`，动态适配 batch |
| 2 | ops-nn | `quant_batch_matmul_v3/op_api/aclnn_quant_matmul_v4.cpp` | WeightNz 入口 `CheckDimRange` 的 MX scale 校验从严格相等 `!=3` 改为最小维度 `<4`（强制带 batch，拒绝 dim=3 无 batch） |
| 3 | ops-nn | `quant_batch_matmul_v3/op_api/quant_matmul_checker.cpp` | 5 个 MX 相关函数：维度数校验放宽 + 新增 batch 逐维校验 + 索引批量化 |
| 4 | ops-nn | `op_host/op_tiling/arch35/quant_batch_matmul_v3_checker.cpp/.h` | 2 个 shape check 函数放宽 + 索引批量化，新增 `CheckBatchValidInMxPerGroupMode` 及其声明 |
| 5 | ops-tensor | `include/blaze/gemm/kernel/kernel_qbmm_mx.h` | **Blaze 路径**：`AddBatchOffset` 新增 pertokenScale/scale GM 指针 batch 偏移（CANN≥9.1） |
| 5b | ops-nn | `matmul/common/cmct/kernel/kernel_qbmm_mx.h` | **CMCT 路径**：`AddBatchOffset` 新增 X1SCALE/X2SCALE tuple 偏移（CANN 9.0，与 #5 对称、公式相同） |

改动量都很小（单点 2-20 行），核心工作量集中在改动点 3、4 的索引批量化与 batch 校验新增。#5 与 #5b 是同一处偏移逻辑在两条 kernel 路径的两份实现，公式必须同步（详见 2.1.4 与 2.6 节）。host 侧 #1-#4 路径无关，两路径完全复用。

## 2.2 torch 层

文件：`op-plugin/op_plugin/ops/opapi/QuantMatmulKernelNpuOpApi.cpp`

该层做两件事：调用路由与 transpose 校验。路由部分对 MX FP8×FP8 按 x2 格式分流（ND→V5，NZ→WeightNz），无需改动。

需改动的是 transpose 一致性校验 `is_x_scale_same_transpose`：MX（FLOAT8_E8M0）场景需要正确计算 scale 的 M/N 维索引。Perblock 模式 scale 尾巴为 2 维，索引用 `dim()-2`；MX 模式 scale 尾巴为固定 3 维，索引必须用 `dim()-3`。改造即把 MX 分支的 `dim_scale` 基准从固定 0 改为 `dim()-3`。

设计理由：`dim()-3` 能动态适应任意 batch 层数（减去 MX 固定 3 维）。接口层强制带 batch，`dim ≥ 4`，`dim()-3 ≥ 1`。

## 2.3 aclnn 入口层

文件：`quant_batch_matmul_v3/op_api/aclnn_quant_matmul_v4.cpp`（含 V3/V4/WeightNz 三入口，MX FP8×FP8 NZ 走 WeightNz）。

改动函数：`CheckDimRange`（参数第一道粗筛 gate）。

当前问题：gate 用严格相等宏校验 MX scale 维度数必须等于 3，导致 scale dim≥4（带 batch）时在第一道关卡就被直接拦截，后续 checker 的 batch 感知校验根本跑不到。

设计：MX scale 由 3 个固定基础维 `(M或K, ceil(.../64), 2)` + batch 前缀构成，且接口层强制必须带 batch（至少 1 层）。因此维度约束应为"至少 4 维"——`<4` 非法（含 dim=3 无 batch，已不再支持）、`=4` 1 层 batch、`>4` 多层 batch。改造即把 MX 场景的严格相等校验替换为最小维度校验，下限由 3 提升为 4（`MX_SCALE_DIM_NUM` 值由 3 改为 4）；非 MX 分支保持原有严格相等不变。

为什么只做粗筛、不在这层做精细 batch 校验：`CheckDimRange` 只能拿到 tensor 指针，没有 batch 模式信息（isPerblock/isMxPerGroup）和 pertokenScale，无法判断 batch 维值是否与 x1/x2 对齐。精细的 batch 逐维校验留给后续 checker 层完成。

为什么无需约束上界：同函数内 x1/out 已有 ≤6D 限制，且后续 checker 会做 `scaleBatchDim == xBatchDim` 严格对齐，x1≤6 隐含 scale≤7，上界自然收敛。

附带说明：同文件的 `MxScaleContiguousProcess` 已使用 `dimNum-1/-2/-3/-4` 相对索引，天然兼容 batch 前缀，无需改动。

维度放行情况：MX 无 batch（dim=3）旧逻辑通过、新逻辑拒绝（不再支持）；MX 带 batch（dim 4/5/7）旧逻辑拒绝、新逻辑通过；MX 非法（<3）新旧均拒绝；非 MX 走 else 分支不受影响。

## 2.4 Checker 层

文件：`op_api/quant_matmul_checker.cpp`。在 aclnn 入口粗筛放行后执行，负责 shape / dtype / dim 值的精细校验。涉及 MX 的函数共 5 个：

| 函数 | 职责 | 改造 |
|------|------|------|
| `CheckMxScaleDimRange` | scale 维度数校验 | 下限 `<3`→`<4`（强制带 batch） + 新增 batch 逐维校验 |
| `CheckDimValueMicroScaling` | M/K/N/Last 各维值与 x1/x2 对齐 | 索引批量化 |
| `InferGroupSizeM/K/N` | 从 scale 维度反推 groupSize | MX 分支索引加 batch 偏移 |

`CheckMxScaleDimRange`：把维度数下限校验从 `< MX_SCALE_DIM(3)` 提升为 `< MX_SCALE_MIN_DIM_WITH_BATCH(4)`（强制带 batch，拒绝 dim=3 无 batch），并新增两步 batch 校验——先按"scale 去掉 MX 固定 3 维 = x1/x2 去掉最后 2 维"的公式校验两边 batch 维数相等，再逐 batch 维比较 scale 与 x1/x2 的维值是否一致。注意 batchDimNum 仍按 `scaleDim − MX_SCALE_DIM(3)` 计算（减固定 3 维不变）。维数对齐是核心不变式：MX scale 的 batch 维数 = scaleDim − 3，x 的 batch 维数 = xDim − 2，二者必须相等且 ≥ 1。

`CheckDimValueMicroScaling`：把硬编码的 M/K/N 维索引改为 `batchDimNum + offset`，把硬编码的最后一维位置（原固定为 2）改为 `dimNum − 1`。值比较逻辑（含 shape-has-one 的转置放开规则）完全不动——这些比较用的是按索引取出的值，索引变了取出的值自动跟随，因此无需改动比较本身。接口层已强制带 batch，`batchDimNum ≥ 1`。

`InferGroupSizeM/K/N`：仅 MX 分支的 scale 维索引统一加 `batchDimNum` 偏移。非 MX 分支以及 `inputSizeM/K/N` 已使用 `dimNum-1` 等相对索引，天然兼容，无需改动。

## 2.5 Tiling Checker 层

文件：`op_host/op_tiling/arch35/quant_batch_matmul_v3_checker.cpp` 与 `.h`。这是 tiling 计算前的最后一道校验，在 api checker 之后执行。涉及 MX 的函数共 4 个（含 1 个新增）：

| 函数 | 职责 |
|------|------|
| `MxPertokenScaleShapeCheck` | pertokenScale 维度数 + M/K/Last 值校验 |
| `MxScaleShapeCheck` | scale 维度数 + K/N/Last 值校验 |
| `CheckInputValidInMxPerGroupMode` | MX per-group 综合校验（签名需扩展） |
| 新增 `CheckBatchValidInMxPerGroupMode` | MX 模式 batch 逐维匹配 |

前两个 shape check：与 checker 层同模式，维度数下限由 `<3` 提升为 `<4`（强制带 batch），M/K/N 索引加 `batchDimNum`（仍按减固定 3 维计算）。

### 为什么必须新写独立的 batch 校验函数

不能复用 Perblock 已有的 `CheckBatchValidInPerblockMode`，原因是 batch 维数计算公式相差 1：

- Perblock 模式：scale 的 shape 完全等于 x1/x2 的 shape（尾巴都是 2 维），两边 batch 维数公式都是 `dim − 2`。
- MX 模式：scale 尾巴是固定 3 维 `(ceil(K/64)或M, N或..., 2)`，而 x1/x2 尾巴仍是 2 维。scale 的 batch 维数是 `dim − 3`，x 的是 `dim − 2`。

若错误地套用 Perblock 的 `dim − 2` 去算 MX scale 的 batch，会把 `ceil(K/64)` 这一维也误计入 batch，导致 batch 维数多算、校验跑偏。核心逻辑与 Perblock 模板一致，仅 batch 维数公式不同（`-3` vs `-2`），故必须独立成函数。

`CheckBatchValidInMxPerGroupMode` 的逻辑：对 scaleX2/pertokenScale 分别按 `dim-3` 算 batch 维数、对 x2/x1 按 `dim-2` 算，先校验维数精确相等，再逐 batch 维比较维值，任一不符即报错返回。

### 签名扩展

`CheckInputValidInMxPerGroupMode` 原签名不含 x1Shape/x2Shape，无法把 x 的 shape 传给新的 batch 校验函数。改造为在签名中新增 x1Shape/x2Shape 两个入参，并在两个 shape check 之后调用新函数；x1Shape/x2Shape 在调用方同函数内已可获取，直接透传即可。

### Tiling Data：无需新增字段

`QuantBatchMatmulV3BasicAPIDataParams` 现有 `batchA1-4` / `batchB1-4` / `batchC1-4`（命名规则 `batch<矩阵><层级>`，A=x1、B=x2、C=out，1-4 由最外层到紧贴 M/K/N 的最内层，且 `batchA = batchA1×batchA2×batchA3×batchA4`）已完整描述 x1/x2 的 batch 结构。

设计决策：不新增任何 tiling 字段。理由是 scaleX1 batch 等于 x1 batch、scaleX2 batch 等于 x2 batch，尺度信息（M/K/N）已在 problemShape 中，kernel 可自行用 batch offset 乘以 scale 单 batch 元素数计算 stride；且 broadcast 语义通过复用 `batchAOffset_`/`batchBOffset_` 自动继承，无需单独维护。

## 2.6 Kernel 层

文件：QBMM 的 MX kernel 由 `IS_BLAZE` 宏二选一，scale batch 偏移需在两条路径对称落地：
- Blaze 路径（CANN≥9.1）：ops-tensor 仓 `include/blaze/gemm/kernel/kernel_qbmm_mx.h`（改动点 5）。
- CMCT 路径（CANN 9.0）：ops-nn 仓 `matmul/common/cmct/kernel/kernel_qbmm_mx.h`（改动点 5b）。

路径选型说明：两条路径的 `AddBatchOffset` 当前都已为 x1/x2/out/bias 做 batch 偏移，唯独 pertokenScale/scale 缺失。本设计在两份内核中实施等效改动（`batchOffset × 单batch元素数`），fp8/fp4 均覆盖。两份逻辑必须同步，公式相同（见下文 stride 公式）。

### batch 偏移机制

kernel 持有 6 个 GM 指针（x1/x2/out/bias/pertokenScale/scale）和 3 个 batch 偏移计数器（batchAOffset_/batchBOffset_/batchCOffset_）。外层有 4 层嵌套 batch 循环，每轮 iteration：先 `ResetGmAddr` 把所有指针复位到基地址，再 `AddBatchOffset` 按当前计数器累加 batch 偏移，然后处理单个 batch。

关键点：`batchAOffset_` 与 `batchBOffset_` 不一定相等。它们的含义不是"第几个 batch"，而是"当前 A/B 矩阵的数据索引"，由 broadcast 比率（`multiA*C*` / `multiB*C*`）修正。例如 x1=(3,M,K)、x2=(1,K,N) 时 B 在 batch 维广播，batchAOffset_ 逐轮 0,1,2，而 batchBOffset_ 恒为 0。这正是 scale 能直接复用这两个计数器、自动继承 broadcast 语义的原因。

### 改造内容

当前两条路径的 `AddBatchOffset` 都已为 x1/x2/out/bias 四个指针做了 batch 偏移，唯独 pertokenScale 与 scale 两个缺失偏移，导致它们始终指向第 1 个 batch 的数据。

设计：各新增两行偏移。pertokenScale 跟随 batchAOffset_，单 batch 元素数为 `M × ceil(K/64) × 2`；scale 跟随 batchBOffset_，单 batch 元素数为 `N × ceil(K/64) × 2`。M/N/K 取自 problemShape，ceil 用现有 CeilDiv，常量复用已有的 MX 组大小（64）与基础倍数（2），零新增依赖。

两条路径写法差异（设计无关、实现细节）：Blaze 路径对原始 GM 指针做 `+=`；CMCT 路径对 tuple 偏移 `blockOffset_` 的 X1SCALE/X2SCALE 索引做 `+=`（元素索引、非字节）。公式与语义完全一致。

stride 公式即本设计的核心数据决策：
- pertokenScale batch stride = M × ceil(K/64) × 2
- scale batch stride = N × ceil(K/64) × 2

按 batch 偏移：pertokenScale 跟随 batchAOffset_、scale 跟随 batchBOffset_，每轮 batch iteration 偏移到当前 batch 的数据起点；接口层强制带 batch，偏移恒生效。

无计算逻辑新增：单 batch 内用这两个指针构造 tensor 做乘法的流程不变，仅指针值被修正为正确 batch 的数据起点。

### Kernel Wrapper

文件：ops-nn 仓 `op_kernel/arch35/qbmm_mx_tensor_api_blaze.h`。Wrapper 仅把两个 scale 指针作为 GM 地址透传给 Blaze 内核，batch 偏移在内核 `AddBatchOffset` 中处理，wrapper 传参结构不变，无需改动。

# 3 验证

## 3.1 测试矩阵设计思路

验证分四类，覆盖思路如下：

无 batch 拒绝回归（dim=3，预期报错）：验证接口层强制带 batch 的约束生效。覆盖 FP8/FP4 的 ND/NZ 格式以及带 bias 场景，scale 仍为 3 维（无 batch），预期全部在 aclnn gate（`<4`）被拒绝报错——dim=3 无 batch 已不再支持。

新增 batch 场景：验证 batch 功能正确。覆盖 1/2/4 层 batch（scale 维度对应为 4/5/7 维），以及 A 广播、B 广播两种单边 broadcast——后者专门验证 kernel 中 batchAOffset_/batchBOffset_ 经 broadcast 比率修正后能各自走对数据。

负向用例：验证各拦截层按预期报错。包括 scale dim=2/dim=3（MX 无 batch 或缺基础维，aclnn gate `<4` 拦截）、scale 有 batch 但 x1 无 batch（batch 维数不匹配，checker/tiling 拦截）、scale batch 值与 x1 batch 值不等（逐维校验拦截）、FP4 K=1 非法（既有逻辑拦截）。这组用例正好对应三道校验关卡，确保每层职责边界清晰。

精度验证：FP8/FP4 MX 全量化 batch 场景结果与 float32 参考一致，满足 mxFP 精度标准；同一输入多次运行结果一致，确认无 batch broadcast 竞态。

路径覆盖：scale batch 在 Blaze（CANN≥9.1）与 CMCT（CANN 9.0）两条 kernel 路径都需覆盖。同一组 batch 用例应在目标环境对应的路径上跑通；若两套环境都可用，两条路径都要验证 fp8 与 fp4 的 batch 正确性，确认两份 `AddBatchOffset` 偏移公式一致、无漂移。
