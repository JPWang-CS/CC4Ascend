# MTP 投机解码（Speculative Decoding）通俗详解

## 一、问题背景：大模型推理为什么慢？

### 1.1 传统推理方式

假设你问 ChatGPT："今天天气怎么样？"，它需要生成回答："今天天气很好，阳光明媚。"

**传统方式是一个字一个字蹦出来的**：

```
轮次1: 输入 "今天天气怎么样？" → 生成 "今"
轮次2: 输入 "今天天气怎么样？今" → 生成 "天"
轮次3: 输入 "今天天气怎么样？今天" → 生成 "天"
轮次4: 输入 "今天天气怎么样？今天天" → 生成 "气"
...
轮次12: 输入 "今天天气怎么样？今天天气很好，阳光明" → 生成 "媚"
```

每次只生成 1 个 token（字/词），需要调用 12 次大模型。

### 1.2 为什么慢？

**每次调用大模型都要做一次完整的前向推理**：
- 加载几十 GB 的权重
- 计算几百层 Transformer
- 访问大量显存/内存

即使每次只输出 1 个字，也要跑完整个模型，**非常浪费**。

就像你让建筑工人盖房子，每次只让他搬 1 块砖，搬完就休息，下次再来搬 1 块。效率极低！

## 二、MTP 的核心思想：让小模型先猜，大模型验证

### 2.1 "投机采样"类比

想象你在考试：

1. **小学生**（draft model，轻量级模型）先快速做题，写下答案：`A B C D E F G`
2. **大学教授**（主模型，真正的大模型）检查答案：
   - A ✓ 正确
   - B ✓ 正确  
   - C ✓ 正确
   - D ✗ 错误！从这里开始都不要了
   - E ✗ 丢弃
   - F ✗ 丢弃
   - G ✗ 丢弃
3. **最终结果**：接受前 3 个答案 `A B C`，教授重新写第 4 个答案 `X`

**关键点**：
- 小学生速度快（10 毫秒），但可能错
- 教授速度慢（100 毫秒），但肯定对
- **如果小学生猜对了一部分，就省掉了教授重复计算的时间**

### 2.2 应用到大模型推理

```
问题: "今天天气怎么样？"

【传统方式】大模型一个一个生成：
大模型: "今" → "天" → "天" → "气" → "很" → "好" → ...
耗时: 100ms × 12次 = 1200ms

【MTP 投机方式】小模型先猜 7 个，大模型验证：
第1轮:
  小模型: 快速猜 "今天天气很好阳" (7个字)
  大模型: 验证 "今天天气" (前4个对✓) → 接受，从第5个"很"开始重新生成
  实际接受: "今天天气" (4个) + 大模型纠正 "很" (1个) = 5个字
  
第2轮:
  小模型: 快速猜 "好阳光明媚空气" (7个字)
  大模型: 验证 "好阳光" (前3个对✓)
  实际接受: "好阳光" (3个) + 大模型纠正 "明" (1个) = 4个字

结果: 原本需要12轮，现在只需要3-4轮
耗时: 120ms × 3轮 ≈ 360ms （提速 3.3倍！）
```

## 三、关键参数解释

### 3.1 m (multiTokenNum) - 投机的 draft token 个数

**m 是小模型一次性猜测的 token 数量**。

举例：
- **m = 0**：不使用投机，退化为传统模式（每次只生成1个）
- **m = 7**：小模型一次猜 7 个 token，大模型验证后可能接受 0~7 个
- **m = 16**：小模型一次猜 16 个 token（本次扩展的目标）

**类比**：m 就是小学生一次性写多少道题。

### 3.2 num_accepted_tokens - 实际接受的 token 数

**大模型验证后，实际采纳了几个小模型的猜测**。

举例：
- 小模型猜了 7 个：`A B C D E F G`
- 大模型验证发现前 3 个对：`A✓ B✓ C✓ D✗ ...`
- `num_accepted_tokens[batch_id] = 3`

**类比**：教授批改后，有几道题是对的。

### 3.3 seqLen - 当前输入序列长度

```
seqLen = m + 1
```

为什么 +1？因为输入包括：
- **m 个 draft token**（小模型猜的）
- **1 个当前 token**（大模型要验证的第一个位置）

举例：
- m = 7 → seqLen = 8（7 个猜测 + 1 个起始）
- m = 16 → seqLen = 17

### 3.4 stateLen - 缓存状态长度

```
stateLen = K - 1 + m
```

其中 K = 3（卷积核宽度）。

**为什么需要这么长的缓存？**

因果卷积需要历史数据：
- K - 1 = 2：卷积需要向前看 2 个 token
- m：投机猜测的 token 也需要缓存

举例：
- K = 3, m = 7 → stateLen = 2 + 7 = 9
- K = 3, m = 16 → stateLen = 2 + 16 = 18

## 四、fused_causal_conv1d 算子在 MTP 中的作用

### 4.1 算子的位置

在 Mamba / SSM 模型中，每一层都有一个**一维因果卷积**模块，用于捕获序列的局部依赖。

```
输入序列 → 投影 → 因果卷积 → 激活 → SSM → 输出
                    ↑
              fused_causal_conv1d
```

### 4.2 算子需要处理的数据

**场景**：decode 阶段，投机解码模式

假设：
- 当前正在生成第 100 个 token
- 小模型猜了 7 个：token_101, token_102, ..., token_107
- 大模型需要验证这 7 个 + 生成第 100 个

**算子的输入**：
```python
x: [batch, seqLen, dim]
   = [1, 8, 1024]  # 1个batch, 8个token (1当前+7猜测), 1024维度

conv_states: [batch, stateLen, dim]
            = [1, 9, 1024]  # 缓存前 9 个 token 的历史状态
            
num_accepted_tokens: [batch]
                    = [3]  # 上一轮接受了 3 个 draft token
```

**算子的工作**：

1. **读取历史缓存**：
   - 因为上一轮接受了 3 个 token，需要从 `conv_states` 中读取对应的历史状态
   - `offset = num_accepted_tokens[0] - 1 = 3 - 1 = 2`
   - 读取 `conv_states[0:offset+K-1]` = `conv_states[0:4]`（前 4 个历史状态）

2. **拼接输入**：
   ```
   paddedInput = [历史4个 | 当前输入8个] = 12个token
   ```

3. **执行卷积**：
   - 用 K=3 的卷积核在 paddedInput 上滑动
   - 对每个位置计算：`output[i] = sum(paddedInput[i:i+3] * weight)`
   - 生成 8 个输出

4. **更新缓存**：
   - 把最新的状态（最后 9 个 token）写回 `conv_states`
   - 为下一轮推理做准备

### 4.3 图示过程

```
时刻 t-1 (上一轮):
conv_states: [s1, s2, s3, s4, s5, s6, s7, s8, s9]  <- 保存着历史状态
                                ↑
                         接受了3个token (offset=2)

时刻 t (当前轮):
输入 x: [t0, t1, t2, t3, t4, t5, t6, t7]  <- 8个token (1当前+7猜测)

根据 offset=2，从 conv_states 读取前 4 个:
历史状态: [s1, s2, s3, s4]

拼接:
paddedInput: [s1, s2, s3, s4 | t0, t1, t2, t3, t4, t5, t6, t7]
              ←— 历史 4个 —→  ←————— 当前输入 8个 ————→

卷积 (K=3):
output[0] = conv([s3, s4, t0])  ← 需要前2个历史状态
output[1] = conv([s4, t0, t1])
output[2] = conv([t0, t1, t2])
...
output[7] = conv([t5, t6, t7])

更新缓存 (保存最新的9个):
conv_states: [t0, t1, t2, t3, t4, t5, t6, t7, output[7]]
```

## 五、为什么要从 m=7 扩展到 m=16？

### 5.1 更大的投机窗口 = 更高的吞吐

假设小模型的准确率是 70%（每个 token 有 70% 概率猜对）：

| m  | 平均接受数 | 每轮生成 token 数 | 加速比 |
|----|------------|-------------------|--------|
| 0  | 0          | 1                 | 1.0×   |
| 7  | ~3-4       | 4-5               | 4-5×   |
| 16 | ~6-8       | 7-9               | 7-9×   |

**关键**：m 越大，一次能猜越多，命中率高时加速越明显。

### 5.2 Pangu V2 模型的需求

Pangu V2 在 Dflash 投机采样中发现：
- 当前 m=7 时，投机窗口不够大
- 小模型在某些场景下准确率很高（>80%），可以猜更多
- **提升到 m=16，吞吐可以再提升 50%-100%**

### 5.3 权衡

更大的 m 也有代价：

**好处**：
- ✅ 命中时加速更明显
- ✅ 吞吐提升

**代价**：
- ❌ UB buffer 需求增加（stateLen 从 9 → 18）
- ❌ 单次 kernel 性能略降（循环次数增加 ~18%）
- ❌ 如果小模型准确率低，浪费更多计算

**总体**：对于准确率高的场景，m=16 是净收益。

## 六、本次改动的本质

### 6.1 改动前

```cpp
// op_host/ai_infra_fused_causal_conv1d_tiling.h
constexpr int64_t MAX_M = 7;  // 最多猜 7 个
constexpr int64_t MAX_DECODE_LEN = 8;  // seqLen 最大 8

// 校验逻辑
if (multiTokenNum > 7) {
    报错: "m 不能超过 7"
}
```

**限制**：
- ❌ 不能处理 m > 7 的输入
- ❌ conv_states 的 stateLen 最大 9

### 6.2 改动后

```cpp
constexpr int64_t MAX_M = 16;  // 最多猜 16 个
constexpr int64_t MAX_DECODE_LEN = 17;  // seqLen 最大 17

// 校验逻辑
if (multiTokenNum > 16) {
    报错: "m 不能超过 16"
}
```

**放宽限制**：
- ✅ 支持 m ∈ [0, 16]
- ✅ conv_states 的 stateLen 最大 18
- ✅ 新增 `maxDraftTokens` 参数，让用户指定需要多大的投机窗口

### 6.3 为什么不直接改成无限大？

**UB buffer 是有限的**（~256KB）。

如果 m 无限大：
- stateLen 无限大
- UB buffer 需求无限大
- 单次只能处理很少的 dim，循环次数暴增
- **性能反而会崩溃**

所以需要一个合理的上限（16 是根据 Pangu V2 模型的实测需求确定的）。

## 八、常见疑问

### Q1: 小模型猜错了怎么办？

**不影响正确性**。大模型验证时，遇到第一个错误就停止，从那里重新生成。

就像教授批改作业，发现第 4 题错了，就从第 4 题开始重做，前 3 题的正确答案保留。

### Q2: 为什么不直接用大模型生成多个 token？

**大模型太慢了**。生成 1 个 token 和生成 7 个 token 的时间差不多（都要跑完整个模型）。

MTP 的核心是**用快速的小模型做粗筛，大模型只做验证和纠错**，这样才能加速。

### Q3: 所有场景都适合 MTP 吗？

**不一定**。MTP 适合：
- ✅ 输出可预测性强的场景（如代码生成、翻译）
- ✅ 小模型准确率高（>50%）
- ❌ 不适合创意性写作（小模型很难猜对）

### Q4: conv_states 是什么？

**缓存的历史状态**。

因果卷积需要"回看"前几个 token 的数据（K-1 个），再加上投机猜测的 m 个 token，所以需要缓存 `K-1+m` 个历史状态。

类比：你做作业时，需要看前面的几道题（K-1），还要预留空间给草稿纸（m）。
