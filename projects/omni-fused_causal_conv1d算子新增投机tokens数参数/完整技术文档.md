## 一、算子概述与定位

### 1.1 算子做什么

`fused_causal_conv1d` 是一个**融合算子**，对输入序列执行因果一维卷积（causal conv1d），同时融合：

1. **缓存状态读写**（conv_states）：每个 batch 维护一份历史 token 缓存，卷积前从缓存读"窗口前缀"，卷积后把新 token 写回缓存。
2. **激活函数**（SiLU/Swish）：卷积结果可选过激活。
3. **残差连接**（residual）：卷积结果加回输入 `y = conv(x) + x`。
4. **原地更新**（inplace）：结果直接写回 `x` 的 GM，省一次 copyout。
5. **APC（Aggressive Prefix Cache）**：block 级 cache 行管理，跨调度 chunk 复用 cache。
6. **MTP（Multi-Token Prediction）投机解码**：一次 forward 处理 m+1 个 token（而非单 token decode），提升吞吐。

### 1.2 网络定位

- **模型**：Pangu V2 92B / 505B
- **场景**：推理，Dflash 投机采样
- **位置**：在 LLM 的 embedding 后、attention 前；是 SSM/Hybrid 架构（Mamba2 + Attention 混合）里 SSM 层的核心算子之一
- **TP 切分**：dim 维度按 TP 切（dim/TP），与 m 无关；DP/EP/CP 不影响算子接口

### 1.3 当前能力 vs 本次扩展

| 维度 | 当前（m ≤ 7） | 本次扩展后（m ≤ 16） |
|---|---|---|
| multiTokenNum (m) | [0, 7] | [0, 16] |
| stateLen (K=3 时) | [2, 9] | [2, 18] |
| MAX_DECODE_LEN | 8 | 17（= MAX_M + 1） |
| 接口签名 | 无 maxDraftTokens | **新增 `maxDraftTokens`（默认7，[0,16]）** |
| UB buffer 占用 | stateLen ≤ 9 | stateLen ≤ 18，buffer 翻倍（CUTBS/Update 路径） |

## 二、投机解码（MTP）与前缀缓存（APC）原理

### 2.1 MTP（Multi-Token Prediction）投机解码

**传统 decode**：一次 forward 只处理 1 个 token（自回归）。

**MTP 投机解码**：
1. **Draft 阶段**：用一个小模型（draft model）快速生成 k 个候选 token（k ≤ m）。
2. **Verify 阶段**：用大模型一次 forward 验证这 k 个候选，接受前 a 个（a ≤ k）。
3. **收益**：a > 1 时，一次 forward 推进 a 个 token，吞吐提升。

对应到算子参数：

| 参数 | 含义 | 维度 |
|---|---|---|
| `m` (multiTokenNum) | **预留的最大 draft 槽位数**（编译/tiling 期约束） | scalar，由 `conv_states.shape[1] - (W-1)` 隐式编码 |
| `num_accepted_tokens` | **本次 forward 实际接受的 token 数**（运行时 per-batch 可变） | `[B]` int32 |
| `seqLen` | 本次 forward x 的 token 数 = m+1（3D 输入）或 `query_start_loc[i+1]-query_start_loc[i]`（2D 输入） | - |

**易混点**：m 是"槽位上限"，`num_accepted_tokens` 是"实际值"。本次扩展**只放宽 m 的上限**，不动 `num_accepted_tokens` 语义。约束 `accepted ≤ m+1` 依然成立。

### 2.2 stateLen 与 m 的关系

`conv_states` shape 为 `[B, stateLen, D]`，其中：

```
stateLen = (windowSize - 1) + m
```

- `windowSize` = 卷积核 K（K ∈ [3,6]）
- `windowSize - 1` = 卷积需要的"历史窗口"长度（K=3 时需要 2 个历史 token）
- `m` = 额外预留的 draft token 槽位

K=3、m=7 时 stateLen=9；K=3、m=16 时 stateLen=18。**stateLen 是 UB buffer 占用的直接决定因素**。

### 2.3 APC（Aggressive Prefix Cache）

APC 是 block 级 cache 管理：

- `cache_indices` 从 1D `[B]` 变 2D `[B, maxNumBlocks]`，每个 batch 有多个 cache block 槽位。
- `block_idx_first_scheduled_token` / `block_idx_last_scheduled_token`：本次调度 chunk 在 cache block 序列里的起止索引。
- `initial_state_idx`：读 cache 的起始 block 索引。
- `block_size`：单个 cache block 容纳的 token 数（典型 128/256）。

APC 让"跨调度 chunk 复用 cache"成为可能——上一次调度结束的 block 直接作为下一次的 initial state，无需重算。

### 2.4 offset 计算（MTP + APC 联动）

kernel `CalRunningCacheRWIdx`（`op_kernel/ai_infra_fused_causal_conv1d_update.h:179+`）：

```
非 APC：
  readCacheLine = cache_indices[batch]  (或 batch 本身)
  writeRunCacheLine = readCacheLine

APC：
  readCacheLine = cache_indices[batch, initial_state_idx]
  writeRunCacheLine = cache_indices[batch, idx_last]

# num_accepted_tokens 决定读偏移（MTP）
offset = num_accepted_tokens - 1  (把"上一次未消费完的 cache"对齐回正确位置)
```

`num_accepted_tokens` 影响 cache 读偏移；m 影响 cache 容量预留。**两者正交**。

## 四、算子执行流程

### 4.1 runMode 判定（tiling.cpp:101）

```cpp
runMode_ = maxQueryLen_ > MAX_DECODE_LEN || maxQueryLen_ <= 0 ? 0 : 1;
```

- `maxQueryLen > MAX_DECODE_LEN`（>17 本次后）→ **prefill 模式**（0）
- 否则 → **decode 模式**（1）

本次 `MAX_DECODE_LEN` 8→17 是为了保证 m=16 时（`max_query_len = m+1 = 17`）仍走 decode 路径，不被误判为 prefill。

### 4.2 TilingKey 选择（tiling.cpp:499-514）

```
prefill (runMode=0):
  cuSeqLength < coreNum 或 dimSize >= MAX_DIM_CUTBSD(3152) → TilingKey=0 (CUTBSD)
  否则 (cuSeqLength >= coreNum 且 dimSize < 3152)         → TilingKey=1 (CUTBS)

decode (runMode=1):
  xDimSize == 2 或 3                                      → TilingKey=2 (UPDATE_X_BSH)
```

> **注意**：需求文档 §2.6 mermaid 图写 `dimSize < 512` 选 CUTBS，**实际代码阈值是 `MAX_DIM_CUTBSD = 3152`**（`tiling.h:93`），不是 512。需求文档简化了。

### 4.3 三个 kernel 模板对比

| 模板 | TilingKey | 场景 | stateLen 依赖 | m 扩展影响 |
|---|---|---|---|---|
| **CUTBSD** | 0 | prefill, dim 大（≥3152）或 cuSeqLen 小 | **不依赖** | 不受影响 |
| **CUTBS** | 1 | prefill, dim 小（<3152）且 cuSeqLen 大 | cacheQue + cacheBuf 与 stateLen 成正比 | UB +24KB，ubFactor 28→24，循环 +18% |
| **Update** | 2 | decode（MTP 走这里） | convStatesQueue 与 stateLen 成正比 | maxDim -25.5%，dim 切分增加 |

### 4.4 整体调用链

```
PyTorch torch_npu.npu_ai_infra_fused_causal_conv1d(...)
  ↓ (torch binding, EXEC_NPU_CMD_V1)
```

## 五、Kernel 实现要点

源文件：`op_kernel/ai_infra_fused_causal_conv1d_{update,fn_cutbs,fn_cutbsd,common}.h`

### 5.1 Update 模板（decode + MTP，本次重点）

文件：`op_kernel/ai_infra_fused_causal_conv1d_update.h`

**InitBuffer（:96-103）**：

```cpp
this->pipe_->InitBuffer(xQueue_,            DOUBLE_BUFFER_NUM, curDim_ * sizeof(DTYPE));
this->pipe_->InitBuffer(weightQueue_,       NUM_ONE,           kWindowSize * curDim_ * sizeof(float));
this->pipe_->InitBuffer(convStatesQueue_,   NUM_ONE,           stateLen_ * curDim_ * sizeof(DTYPE));  // ★ 随 m 线性增长
this->pipe_->InitBuffer(outputQueue_,       NUM_ONE,           curDim_ * sizeof(DTYPE));
this->pipe_->InitBuffer(yBuf_,              kWindowSize * curDim_ * sizeof(float));
this->pipe_->InitBuffer(xBuf_,              curDim_ * sizeof(float));
```

**Process 主循环（:106-152）**：

```
CopyInWeight()              // 搬 weight、原地 cast fp32、silu 时 w[K-1] += 1（残差预加）
for idxB in curBatch_:
    CalRunningCacheRWIdx()   // 算读/写 cache 行（APC vs 非 APC 分支）
    if readCacheLine == padSlotId: continue   // 跳过 pad batch
    CopyInConvState()        // 搬旧 cache 到 convStatesLocal_
    CopyOutConvStateRunCache()   // 写 running cache 中本就是 cache 的部分
    CopyOutConvStatePreCache()
    InitY()                  // y0/y1 累加器清零
    for idxS in seqLen_:     // 逐 token（MTP 下 seqLen = m+1）
        CopyInX(idxS)
        CopyOutXRunCache(idxS)    // 写回 cache（更新状态）
        CopyOutXPreCache(idxS)
        ComputeAndUpdate(idxS)    // 卷积步进：y += w[t] * x, t=0..W-1
        CopyOutY(idxS)
```

**关键点**：kernel **不直接消费 m**，它消费 `seqLen_ = m+1`（3D）或 `query_start_loc[i+1]-query_start_loc[i]`（2D）。m 是隐式 shape 约束，由 tiling 期 `multiTokenNum_ = x.shape[1] - 1`（`tiling.cpp:159`）或 `stateLen - (W-1)`（:245）反推。

### 5.2 CUTBS 模板（prefill, dim 小）

| cacheBuf | 9×512×2B = 9KB | 18×512×2B = 18KB | +9KB |
| **合计** | 27KB | 54KB | **+27KB** |

### 5.3 CUTBSD 模板（prefill, dim 大）

文件：`op_kernel/ai_infra_fused_causal_conv1d_fn_cutbsd.h`

**特点**：逐 token 计算，buffer 不依赖 stateLen。`convStatesQue` 大小 = `2 × baseDim × sizeof(DTYPE)`（与 m 无关）。**本次扩展不受影响**。

### 5.4 卷积滑动窗口语义

因果卷积：对位置 t 的输出，只用 `[t-W+1, t]` 范围的输入（W=kernelSize）。

```
y[t] = sum_{k=0}^{W-1} weight[k] * x[t - k]    (+ bias, + residual, * activation)
```

cache 的作用：当 `t - k < 0`（序列开头）时，从 `conv_states` 读历史 token 补齐。MTP 下 cache 还要保存"上一次未消费完的 draft token"。

## 六、Golden 代码逐段解析

### 6.1 现有 golden 源

主 oracle：`D:\Desktop\Code\CustomOP\atk\AiInfraFusedCausalConv1d\executor_ai_infra_fused_causal_conv1d_continue.py:73` `causal_conv1d_golden()`。

纯 PyTorch 参考实现，逐 batch 处理：

```python
def causal_conv1d_golden(x, weight, conv_states, query_start_loc, cache_indices,
    max_query_len=-1, pad_slot_id=-1,
    num_accepted_tokens=None, num_computed_tokens=None,
    block_idx_first_scheduled_token=None, block_idx_last_scheduled_token=None,
    initial_state_idx=None, B_size=128,
    conv_mode=1, inplace=False, residual=True) -> torch.Tensor:

    # 3D 输入先 flatten 到 2D
    if x.ndim == 3:
        bsz, seq_len, dim = x.shape
        x = x.view(-1, dim)
        query_start_loc = torch.arange(0, (bsz+1)*seq_len, seq_len, dtype=torch.int32)

    cu_seq_len, dim = x.shape
    batch_size = query_start_loc.shape[0] - 1
    width = weight.size(0)
    out = torch.zeros_like(x)

    for batch_idx in range(batch_size):
        start_idx = query_start_loc[batch_idx].item()
        end_idx = query_start_loc[batch_idx + 1].item()
        seq_len = end_idx - start_idx
        seq_x = x[start_idx:end_idx]   # [seq_len, dim]

        # APC 分支：算 cache 读写行、block 偏移
        if apc_enabled:
            seq_completed_offset_token = num_computed_tokens[batch_idx].item() % B_size
            seq_completed_offset = B_size - seq_completed_offset_token
            seq_end_offset = (seq_len - seq_completed_offset) % B_size
            last_full_block_token_index = seq_len - seq_end_offset
            ...
            read_cache_line = cache_indices[batch_idx, initial_state_idx[batch_idx]].item()
            write_cache_line = cache_indices[batch_idx, idx_last].item()
        else:
            read_cache_line = cache_indices[batch_idx].item() if has_cache_indices else batch_idx
            write_cache_line = read_cache_line

        # MTP offset：num_accepted_tokens 决定 cache 读偏移
        offset = num_accepted_tokens[batch_idx].item() - 1 if has_nat else 0

        # 读 cache（W-1 个历史 token + offset 对齐）
        cached_state = conv_states[read_cache_line][: offset + width - 1]
        padded_input = torch.cat([cached_state, seq_x], dim=0)   # 前拼历史

        # 写 cache（尾对齐）
        cache_len = min(conv_states.shape[1], seq_len + offset + width - 1)
        conv_states[write_cache_line][-cache_len:] = padded_input[-cache_len:]

        padded_input = padded_input[offset:]   # 去掉对齐部分

        # 卷积（grouped conv，每个 dim 维度独立卷积）
        result = F.conv1d(padded_input.T.unsqueeze(0), weight.T.unsqueeze(1),
                          groups=dim, stride=1, padding=0).squeeze(0).T

        # Pangu V2 reset：conv_mode=1 时前 (W-1-num_computed) 个置 0
        if conv_mode == 1:
            last_reset_idx = width - 1 - num_computed_tokens[batch_idx].item()
            last_reset_idx = max(0, min(last_reset_idx, seq_len))
            result[:last_reset_idx] = 0

        out[start_idx:end_idx] = result + seq_x if residual else result

    return out
```

### 6.2 golden 对 m 的覆盖现状

atk 11 个 json 配置（`*_continue.json`、`*_no_continue.json`、`*_pref.json`、`*_npugraphex_*`、`*_sk_aclgraph*`、`*_seqlen0_A3*`）的 `conv_states.shape[1]` 实测：

| case 类型 | stateLen | m (= stateLen - 2, K=3) |
|---|---|---|

| continue case 3-5 (BSH) | 5 / 2 / 5 | 3 / 0 / 3 |
| fuzz case 6-8 | 5 | 3 |

**全部 m ∈ {0, 3}，没有任何 m ∈ [8, 16] 的覆盖**。本次扩展必须新增。

### 6.3 扩展到 m ∈ [8,16] 的具体改法

**Golden oracle 本身不需改逻辑**——`causal_conv1d_golden` 已按 shape 动态处理任意 m（`padded_input` 长度自动伸缩）。需要做的是：

1. **新增 caseData** 覆盖 m ∈ {8, 12, 16} 三个代表点 + 边界 m=0/1 回归。
2. **构造 `num_accepted_tokens` 与 m 的合法组合**：
   - `accepted ∈ [1, m+1]`（kernel 隐含约束）
   - 阴性对照：`accepted > m+1`（应被 kernel 拒绝）
3. **APC + 大 m 跨多 block 写 cache**：`n_block_to_fill = idx_last - idx_first` 可能 >1，覆盖跨 block 场景。
4. **D × m 二维扫描**：D ∈ {64, 1024, 8192, 16384} × m ∈ {0, 7, 8, 16}，重点验证大 D + 大 m UB 不溢出。

### 6.4 判据

参考 atk json 的 `cv_fused_double_benchmark`（双标杆 ratio）：

```json
"standard": {
  "acc": {
    "cv_fused_double_benchmark": {
      "max_re_ratio": 5,
      "avg_re_ratio": 1.5,
      "root_mean_squared_ratio": 1.5
    }
  }
}
```

即 max相对误差比 ≤ 5、avg相对误差比 ≤ 1.5、RMSE比 ≤ 1.5。这是 fuzz 双标杆（NPU vs GPU）判据。

**无 GPU 时降级**：用 flat `isclose + err_ratio`（参考 omni 仓 matmul golden 经验，dtype=bf16 容差 ~2^-8 ULP 级）。输出有两份（`y` + 写回的 `conv_states`），**两份都要比**——cache 写错不会反映在 y 上，是常见 false-pass。

### 6.5 可证伪设计

- **阳性**：m=16, accepted=8，验证 y 与 conv_states 都对齐 golden。
- **阴性 A**：m=16, accepted=17（越界），期望 kernel 报错或与 golden 不符（保护性 fail）。
- **阴性 B**：m=16 但 `conv_states.shape[1] != W-1+m`（shape 不一致），期望 tiling `:239` 报错。
- **回归**：m=0/1（原 decode 单 token 路径）不应被新改动破坏。

## 七、本次改动详解

### 7.1 主线 A：放宽 m 上限 7→16

#### 7.1.1 常量改动

文件：`op_host/ai_infra_fused_causal_conv1d_tiling.h`

| 常量 | 行 | 改前 | 改后 | 说明 |
|---|---|---|---|---|
| `MAX_DECODE_LEN` | 81 | 8 | 17 | prefill/decode 判定阈值，= MAX_M + 1 |
| `MAX_M` | 85 | 7 | 16 | 投机个数上限 |

> 行号以实际 trace 为准（需求文档 §2.6 表格写的 80/84 行有 1 行偏移）。

#### 7.1.2 校验逻辑

文件：`op_host/ai_infra_fused_causal_conv1d_tiling.cpp`

- `:162` `multiTokenNum_ <= MAX_M` 自动跟随常量，无需单独改。
- `:247` 同上。
- `:155` 报错信息 `MAX_DECODE_LEN + 1` 自动跟随。

#### 7.1.3 UB buffer 自适应（无需改 kernel）

kernel 的 buffer 分配全部基于 tiling data 中的 `stateLen`、`multiTokenNum` 动态计算：

| Kernel | Buffer | 大小公式 | m 增大影响 |
|---|---|---|---|
| Update | `convStatesQueue_` | `stateLen × curDim × sizeof(DTYPE)` | UB 占用线性增长 |
| CUTBS | `cacheQue` | `2 × stateLen × baseDim × sizeof(DTYPE)` | UB 占用线性增长 |
| CUTBS | `cacheBuf` | `stateLen × baseDim × sizeof(DTYPE)` | UB 占用线性增长 |
| CUTBSD | `convStatesQue` | `2 × baseDim × sizeof(DTYPE)` | **不受影响** |

tiling 层三处 UB 预算计算（`tiling.cpp:529-534, 570-572, 594-597`）已动态读取 `stateLen`，**自适应收缩** maxDim/baseDim/ubFactor 保证不溢出。代价是性能劣化（见第八章）。

### 7.2 主线 B：新增 maxDraftTokens attr

#### 7.2.1 为什么需要 maxDraftTokens

`stateLen` 从 shape 隐式推（`conv_states.shape[1]`），每次调用的 UB 占用随实际 m 浮动。问题：

- **ACLGraph capture/replay 不友好**：capture 期 m 被冻结，replay 时若 m 变化会触发动态重 tiling（破坏 graph 性能）。
- **多 batch m 不同**：UB 占用按最大 batch 的 m 算，但 tiling 期不知道。

`maxDraftTokens` 解耦：UB 按 `maxDraftTokens + W - 1` 分配（编译/capture 期固定），实际 m 在 [0, maxDraftTokens] 内变化不触发重 tiling。

#### 7.2.2 全栈透传

| 层 | 改动 |
|---|---|
| **OpDef** | `def.cpp:100` 后加 `this->Attr("max_draft_tokens").AttrType(REQUIRED).Int();`（第 9 个 attr） |
| **tiling.h** | 加 `MAX_DRAFT_TOKENS_INDEX = 8` + `DEFAULT_MAX_DRAFT_TOKENS = 7` + `MIN/MAX_DRAFT_TOKENS` |
| **tiling.cpp** | `GetAttrInfo()` 末尾加解析（value_or(7) + 范围校验） |
| **TilingData** | `tiling.h:132` 后加 `TILING_DATA_FIELD_DEF(int64_t, maxDraftTokens);` |
| **op_api** | `aclnn_...h/cpp` 签名加 `int64_t maxDraftTokens`；`ai_infra_...cpp` l0op `OP_ATTR(..., maxDraftTokens)` 末尾追加 |
| **torch binding** | `npu_...cpp` npu/meta 双签名加 `c10::optional<int64_t> max_draft_tokens`；`value_or(7)` 注入 |
| **torch schema** | `ops_def_registration.cpp:63-70` `m.def(...)` 加 `int max_draft_tokens=7` |
| **UT** | tiling UT 阴性用例阈值改；op_api UT 所有调用加参数 |
| **atk** | 11 个 json 加 `maxDraftTokens` 字段；11 个 executor 调用加参数 |
| **文档** | `docs/aclnn...md` / `docs/npu_...md` 同步签名 + 范围 |

#### 7.2.3 maxDraftTokens 的 UB 用法（两种路径）

| 路径 | 含义 | 实现 | 优劣 |
|---|---|---|---|
| A. 不改 buffer 公式 | stateLen 仍从 shape 推 | 无改动 | 简单；但 ACLGraph 不友好 |
| **B. 用 maxDraftTokens 作 UB 上限** | buffer 维度 = `max(stateLen, maxDraftTokens + W - 1)` | tiling 计算 effectiveStateLen | **推荐**：ACLGraph 友好；代价是 maxDraftTokens > 实际 m 时 UB 略浪费 |

> 待 SE 确认（详见修改清单 §1 C5）。

## 八、性能影响分析

需求文档 §2.6 已给三路径分别分析：

### 8.1 CUTBSD 路径（prefill, dim ≥ 3152）

buffer 不依赖 stateLen，**性能不受影响**。

### 8.2 CUTBS 路径（prefill, dim < 3152）

`cacheQue + cacheBuf` 与 stateLen 成正比：

- stateLen 9→18（K=3, m=7→16）：cacheQue +18KB，cacheBuf +9KB，合计 +27KB（baseDim=512 估算）
- `spaceWithUbfactor` 减小 → `ubFactor_` 28→24（预计）
- 单次 UB 迭代处理的 token 数减少 → **循环次数 +18%**
- **性能劣化**（具体幅度需上板测）

### 8.3 Update 路径（decode + MTP）

`convStatesQueue` 与 stateLen 成正比：

- `spaceWithDim` 增大 → `maxDim` 减小（预计 -25.5%）
- dim 维度核切分数增加 → batch 并行度降低
- **性能劣化**

### 8.4 兼容性保证（需求文档 §2.9 验收）

> "m = 7 或 m 不输入时，单算子性能耗时无劣化。"

即 `maxDraftTokens` 默认值 7（路径 B 下 UB 按 m=7 分配）时，性能与改动前一致。只有显式传 `maxDraftTokens=16` 时才付出 UB 代价。

## 十、常见问题 Q&A

### Q1: MAX_DECODE_LEN 到底是 16 还是 17？

**需求文档自相矛盾**：
- §1.1.3 第41行："MAX_DECODE_LEN 从 8 扩展到 **17**"
- §1.2.3.3 第160行泛化规格表："`MAX_DECODE_LEN = 16`"

**判定**：以 **17** 为准。语义：`MAX_DECODE_LEN = MAX_M + 1 = 16 + 1 = 17`，保证 m=16 时（`max_query_len = m+1 = 17`）仍走 decode 路径，不被误判为 prefill。

**建议**：向 SE 反馈修正泛化规格表（**不改需求文档本身**）。

### Q2: OpDef 里 max_draft_tokens 写 REQUIRED 还是 OPTIONAL？

**现有 8 个 attr 全是 REQUIRED**（`def.cpp:93-100`），没有 OPTIONAL 先例。

**建议 REQUIRED**：
- aclnn checker / GE 入图 / DynamicCompileStatic 流程对 REQUIRED 处理更稳定
- "可选默认 7" 由 aclnn/binding 层 `value_or(7)` 注入
- 与 `max_query_len`/`conv_mode`/`block_size` 一致

### Q3: Python kwarg 用 `maxDraftTokens`（camelCase）还是 `max_draft_tokens`（snake_case）？

需求文档 §2.4.1 用 `maxDraftTokens`（camelCase）。但：
- torch schema 字段名通常 snake_case
- 现有 schema（`ops_def_registration.cpp:63-70`）全是 snake_case（`max_query_len`/`block_size`/`conv_mode`）

**建议**：schema 内部 snake_case `max_draft_tokens`，文档说明 Python kwarg 表面名。若需求方坚持 camelCase，需在 binding 层手动映射（不推荐）。

### Q4: aclnn 签名 maxDraftTokens 插在哪里？

需求文档 §2.4.2 把 `maxDraftTokens` 排在 `initialStateIdx` 之后、`blockSize` 之前（混在 inputs 和 attrs 之间）。

**实际实现建议**：追加到 attrs 末尾（`inplace` 之后、`yOut` 之前）。原因：
- 保持现有"inputs(12) → attrs(8→9) → yOut → workspaceSize → executor"结构
- `OP_ATTR` 宏按顺序绑定，新 attr 必须在 OpDef 注册末尾
- 最小改动 + 编译更稳

需求文档的参数顺序仅是说明用，aclnn C 签名按结构分块更稳。需向 SE 同步（**不改需求文档**）。

### Q5: aclnn 签名变了，老代码怎么办？

签名加参数是**源码级 breaking change**（C 函数签名变了）。但：
- 算子 .so 编译后，调用方都是 omni 仓内部（binding / UT / atk）
- 同步改所有调用方即可
- 对外二进制兼容性：aclnn 是高层 API，签名变更通过版本管理（不是 ABI 兼容范围）

### Q6: maxDraftTokens 大于实际 m 时 UB 浪费怎么办？

路径 B（推荐）下，UB 按 `maxDraftTokens + W - 1` 分配。若 maxDraftTokens=16 但实际 m=7，UB 浪费约 (16-7)/(16+2) ≈ 50%（cacheQue/cacheBuf 部分）。

**缓解**：
- 默认值 7（与现状一致，无浪费）
- 用户按实际 draft 模型能力设置（draft k=8 就传 8，别传 16）
- ACLGraph 场景下 maxDraftTokens 固定，m 在 [0, maxDraftTokens] 内变化不重 tiling，整体收益 > UB 浪费

### Q7: 大 D + 大 m 会 UB 溢出吗？

**不会**（tiling 层自适应保证）。但 dim 切分数增加、性能劣化。

最坏情况估算（D=16384, W=6, m=16, BF16）：
- stateLen = 21
- Update 路径 convStatesQueue = 21 × curDim × 2B
- tiling 自动收缩 curDim（maxDim 自适应），保证 UB 不溢出
- 代价：dim 切分数增加，batch 并行度降低

**需上板验证**（R1 风险）。

### Q8: A5（950）要不要同步改？

**本次不涉及**。需求文档明确 A2/A3 推理。上游 `ops-transformer_AI` 仓有 arch35 路径（`fused_causal_conv1d_cut_bh_tiling_arch35.h:77` 也是 `MAX_M=7`），若后续要扩展到 A5 再同步改。

### Q9: 确定性 / batch 一致性 / 训推一致性 受影响吗？

**不受影响**（需求文档 §2.8 已确认）：
- 确定性：本次不改算法，只放宽约束
- batch 一致性：m 是 per-batch shape 约束，不影响跨 batch 一致
- 训推一致性：仅推理场景，不涉及训练

### Q10: 文档要同步哪些？

- omni 仓 `docs/aclnnAiInfraFusedCausalConv1d.md`：签名 + m 范围 + maxDraftTokens 参数行
