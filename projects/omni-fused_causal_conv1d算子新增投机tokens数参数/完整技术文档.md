## 一、1 分钟看懂这个算子

### 1.1 一句话定义

对输入序列做**因果一维卷积**，同时融合了推理场景必需的三件事：

1. **状态缓存读写**（conv_states）：卷积需要"历史 token"，把它们存进缓存、用完更新
2. **投机解码**（MTP）：一次 forward 处理 m+1 个 token（而非 1 个），提升推理吞吐
3. **混合调度**（PD 混部）：同一个调用里 prefill 和 decode 批次共存

### 1.2 核心公式（只看这一个）

```
y[t] = Σ w[k] · x[t - k],   k = 0, 1, ..., K-1
```

- `K` 是卷积核大小（K ∈ [3,6]），`w[k]` 是核的第 k 行（`[K, dim]`）
- 输出 `y[t]` 只看 `x[t], x[t-1], ..., x[t-K+1]` —— 这就是"因果"：只看自己和过去，不看未来
- 每个 dim 通道独立卷积（`groups=dim` 的 conv1d）
- 可选叠加：残差 `y = conv(x) + x`、激活 SiLU、原地写回 x

### 1.3 为什么因果卷积在 LLM 推理里需要"缓存"

序列很长（上百万 token），但卷积核只有 K=3~6。每个位置的输出只依赖最近 K 个 token——
所以**不需要把整条序列都留在内存里**，只要维护一个 K-1 长的"历史窗口"。

这就是 `conv_states`：`[B, stateLen, D]`，每个 batch 一行，存的是"上次调用结束时序列末尾的历史 token"，下次调用直接读它，不用重算历史。

> 类比：这就像看视频时只记"前两帧"就能判断当前帧的动势，不需要重放整个视频。

### 1.4 算子在网络里的位置

- **模型**：Pangu V2 92B / 505B（SSM/Hybrid 架构，Mamba2 + Attention 混合）
- **场景**：推理，Dflash 投机采样
- **位置**：embedding 后、attention 前 —— SSM 层的核心算子

## 二、核心数学：因果卷积的三种等价写法

同一个卷积，golden 用两种写法验证，kernel 用第三种写法实现。**理解这三者的等价性是读懂整个算子的钥匙。**

### 2.1 写法 A：显式滑窗（朴素定义）

```python
# golden: naive_causal_conv1d_np（golden_fused_causal_conv1d_mtp.py:322）
# 逐 token 逐核累加，直接照抄公式 y[t] = Σ w[k]·x[t-k]
for t in range(L):                        # 序列位置
    for k in range(K):                    # 核内偏移
        if t - k >= 0:                    # 因果性：只累加过去的 token
            y[t, d] += w[k, d] * x[t-k, d]
```

这是"人肉实现"，路径独立、最不可能抄错，用作**双 oracle 之一**。

### 2.2 写法 B：分组卷积（padded_input 前拼历史）

```python
# golden: causal_conv1d_golden_np（golden_fused_causal_conv1d_mtp.py:60）
padded_input = torch.cat([cached_state, seq_x], dim=0)   # [K-1 个历史, 当前 seq_len 个 token]
result = F.conv1d(padded_input.T.unsqueeze(0), weight.T.unsqueeze(1),
                  groups=dim, stride=1, padding=0).squeeze(0).T
```

**核心思想**：因果卷积 = "把历史窗口拼到序列前面，再做普通卷积"。

```
padded_input = [cached_state, seq_x]
                └─ K-1 个历史 ─┘└─ 当前 token ─┘
```

- 拼接后做 `padding=0` 的 conv1d，输出长度 = 输入长度 - K + 1 = seq_len
- 这就是**需求文档 :225-232 的原文公式**，也是 atk executor `causal_conv1d_golden` 的实现，用作**双 oracle 之二**
- 两条代码路径独立（A 是显式循环、B 是 einsum/conv 算子），互相比对可以暴露任何一方的实现错误

### 2.3 写法 C：递推器 / 滑动窗口在线算法（kernel 用这个）

**为什么 kernel 不用 A/B？** A 每算一个 y[t] 要读 K 个 token；B 要先把整个 padded_input 拼好才能算。而 kernel 是**逐 token 流式处理**（token 一个一个从 GM 搬进来），需要"来一个 token 就能输出一个结果"的算法。

**递推器**维护一个长度为 K 的状态数组 `y[0..K-1]`（fp32），每个新 token x 到来时：

```
# 1) 输出当前结果：y[K-1] = y[K-2] + x · w[K-1]
# 2) 滚动更新状态（从高到低）：
#    y[k] = y[k-1] + x · w[k],  k = K-2, ..., 1
#    y[0] = x · w[0]
```

**为什么对？** 展开验证（K=3）：

```
初始:   y[0]=0, y[1]=0, y[2]=0
喂入 x0: y[2]=y[1]+x0·w2 = x0·w2        y[1]=y[0]+x0·w1 = x0·w1   y[0]=x0·w0
喂入 x1: y[2]=y[1]+x1·w2 = x0·w1+x1·w2  y[1]=y[0]+x1·w1 = x0·w0+x1·w1  y[0]=x1·w0
喂入 x2: y[2]=y[1]+x2·w2 = x0·w0+x1·w1+x2·w2   ← 正是 y[2] = Σ w[k]·x[2-k] ✓
```

**kernel 代码位置**（三模板共用同一套递推逻辑）：

| 函数 | 文件:行 | 做什么 |
|---|---|---|
| 递推步进 | `update.h:420` `ComputeAndUpdate` | 每来一个 token 做一次"输出 + 滚动更新" |
| 递推步进 | `fn_cutbs.h:494` `Compute` | 同上（批量版，见下） |
| 递推步进 | `fn_cutbsd.h:463` `Compute` | 同上（逐 token 版） |
| 用缓存喂入递推器 | `update.h:325` `InitY` | 把 cache 的 K-1 个历史 token 依次喂入，恢复 y 状态 |
| 用缓存喂入递推器 | `fn_cutbsd.h:321` `InitY` / `:366` `RestoreY` | 同上（跨核/跨 batch 恢复） |

**残差融合进卷积核**（省一次加法的经典优化，需求文档 :733-742）：

```
w'[K-1] = w[K-1] + 1.0     （kernel 加载 weight 时原地改）
y = Σ w[k]·x[t-k] + x[t]   ← 等价于用 w' 做卷积，直接出残差结果
```

代码：`update.h:173`（`Adds(weight32Local_[K-1], ..., 1.0)`）、`fn_cutbs.h:380`、`fn_cutbsd.h:115`。
注意 w 以 fp32 加载到 UB，所以 `+1.0` 不会引入精度损失。

**SiLU 激活**：`silu(x) = x / (1 + e^-x)`，kernel 用五条向量指令原地算（`common.h:46` ApplySiLU：Adds 保存原值 → Muls 取负 → Exp → Adds 加一 → Div）。

### 2.4 从公式到 golden：逐行对应

golden 不是"另一套东西"——它就是**上面公式的逐行代码化**。以 `causal_conv1d_golden_np`（`golden_fused_causal_conv1d_mtp.py:60`）为例，第二章每个公式在代码里的位置：

| 公式 | golden 代码（:行） | 对应 kernel |
|---|---|---|
| $padded[i] = \begin{cases} cacheState[i], & i < K-1 \\ x[i-(K-1)], & i \ge K-1 \end{cases}$ | `:147` 读 `cached_state = conv_states[read][:offset+K-1]`<br>`:149` `padded_input = np.concatenate([cached_state, seq_x])` | `update.h:214` CopyInConvState |
| $offset = accepted - 1$ | `:143` `offset = accepted_tokens - 1` | `update.h:232-237`（dstLocalOffset 推算） |
| $y[t] = \sum_k w[k] \cdot x'[t+k]$ | `:175-179` 构造滑窗 `windows[t] = padded[t:t+K]`（`np.stack`），<br>再 `np.einsum("tkd,kd->td", windows, weight)` 逐 k 乘累加 | `update.h:420` ComputeAndUpdate（递推器） |
| $cacheState[C-M+i] = x'[Len-M+i],\ M=\min(Len,C)$ | `:152-153` `cache_len = min(C, padded.shape[0])`<br>`conv_states[write][-cache_len:] = padded[-cache_len:]`（尾对齐） | `update.h:268` CopyOutConvStateRunCache / `:380` CopyOutXRunCache |
| APC：$cacheState[idx_k, i] = padded[E-(N-k-1)B+i]$ | `:160-165` `boundary_idx = lfbi-(N-chunk-1)·B`，<br>逐 chunk 写 `cs[wcl][-(K-1):]` | `update.h:301` CopyOutConvStatePreCache / `:396` CopyOutXPreCache |
| Pangu reset：前 $K-1-nct$ 个输出置 0 | `:184-186` `last_reset_idx = K-1-nct`；`result[:lri] = 0` | `update.h:134-138` + `:425` 置零分支 |
| 残差 $y += x$ | `:189` `slot = result + seq_x if residual` | `update.h:173` 残差融合进核（`w[K-1]+=1`），等价 |

**另一个 oracle 的对应**：`naive_causal_conv1d_np`（:322）与上式唯一不同是卷积那步——不用滑窗+einsum，而是显式双层循环（:413-419）：

```python
for t in range(out_len):                 # 对应 y[t]
    acc = np.zeros(dim)
    for k in range(width):               # 对应 Σ_k
        acc += weight[k] * padded[t + k] # 对应 w[k]·x'[t+k]
    result[t] = acc
```

缓存/offset/reset/APC 全部与 atk 版逐行同构（见 :390-410 与 :147-165 的对照），只有卷积走两条独立路径。**两条路径都是上面公式的直接翻译**——正因为如此，互比结果 3190/3190 一致（ratio=0）才有意义：两份"公式的翻译"一致，公式本身没有翻错。

## 三、推理场景：为什么要有 conv_states 缓存

### 3.1 缓存结构

```
conv_states: [B, stateLen, D]
              │     │      └─ dim（与 x 相同）
              │     └─ stateLen = (K-1) + m
              │           K-1: 卷积需要的历史窗口长度（K=3 时是 2）
              │           m:   为 MTP 预留的 draft 槽位数
              └─ batch 索引（也可以是 cache 行索引 cache_indices[b]）
```

**stateLen 是理解本次改动的核心**：它 = 历史窗口 + 投机槽位。K=3 时：

| m | stateLen | 含义 |
|---|---|---|
| 0 | 2 | 纯 prefill，只需 2 个历史 token |
| 7（现状默认） | 9 | 7 个投机槽位 + 2 个历史 |
| 16（本次上限） | 18 | 16 个投机槽位 + 2 个历史 |

### 3.2 读缓存：padding

```
padded_input = [cached_state, seq_x]          # 需求文档 :225
                └─ K-1 历史 ─┘└─ 当前 seq ─┘
```

数学形式（需求文档 :318-328）：

$$
x'[i] = \begin{cases} cacheState[i], & 0 \le i < K-1 \\ x[i-(K-1)], & K-1 \le i < L+K-1 \end{cases}
$$

kernel 里"从哪一行开始读"由 offset 决定（非 MTP 时 `offset = stateLen - (K-1)`，读最后 K-1 个；MTP 时 `offset = accepted - 1`，见第四章）。代码：`update.h:214` `CopyInConvState`、`fn_cutbs.h:420` `CopyInCache`。

### 3.3 写缓存：尾对齐

$$
Len = L + K - 1, \quad M = \min(Len, C) \\
cacheState[C - M + i] = x'[Len - M + i], \quad i = 0, ..., M-1
$$

**尾对齐**：新数据永远写进缓存的**末尾**，最老的数据被顶掉。为什么不是从头写？因为下次读缓存读的是"末尾 K-1 个"，尾对齐保证最新历史在末尾、读偏移固定。

golden 一行对应（`golden_fused_causal_conv1d_mtp.py:153`）：

```python
cache_len = min(conv_states.shape[1], seq_len + offset + width - 1)
conv_states[write_cache_line][-cache_len:] = padded_input[-cache_len:]
```

kernel 对应：`update.h:268` `CopyOutConvStateRunCache`（把"本来就是 cache 的部分"写回 running cache）、`update.h:380` `CopyOutXRunCache`（逐 token 把 x 写回 cache）。

**易错点（golden 为什么要比两份输出）**：`conv_states` 是**写回**的输出。缓存写错不会反映在 `y` 上——比如 cache 偏移差 1，y 计算时读到的历史错位一格，但输出 y 本身看起来"像那么回事"。所以 golden **y 和 conv_states 两份都要比**（`golden_fused_causal_conv1d_mtp.py:874` 双输出互比），防止 cache 错写被 y 的正确掩盖。

### 3.4 首次运行（无历史）

`num_computed_tokens[b] == 0` → 该 batch 序列从零开始，缓存全零（不读 GM）。kernel：`update.h:217`（`Duplicate(0)`），golden：`golden_fused_causal_conv1d_mtp.py:139`。

## 四、MTP 投机解码（Multi-Token Prediction）

> 这就是需求里说的"投机 tokens 数"——**本章是本次改动的核心语义**。

### 4.1 投机解码是什么

**传统 decode**：每步只生成 1 个 token（自回归），串行、慢。

**MTP 投机解码**（需求文档 :31-33）：

```
1. Draft 阶段：小模型（或主模型自带的 MTP 头）快速生成 m 个候选 token
2. Verify 阶段：主模型一次 forward 验证这 m 个候选 + 1 个必然 token，接受前 a 个
3. 收益：接受 a 个就推进 a 个 token，一次 forward 顶 a 次普通 decode
```

**两个关键数字，不要混**：

| 参数 | 含义 | 维度 | 谁决定 |
|---|---|---|---|
| `m`（multiTokenNum） | **槽位上限**：一次 forward 最多验证几个 draft token | shape 隐式（`stateLen-(K-1)` 或 `x.shape[1]-1`） | 编译/调度期固定 |
| `a`（num_accepted_tokens） | **实际接受数**：本次 verify 真正通过几个 | `[B]` int32，per-batch 可变 | 运行时每 batch 不同 |

**接受率**（acceptance rate）是投机解码的关键指标：draft 猜得越准，接受越多，加速越明显。MTP 让主模型自己当 draft（自带 MTP 头），不需要额外的小模型。

### 4.2 m 在 shape 里的位置

**3D 输入**（decode 主路径）：`x = [B, m+1, D]` —— 第二个维度就是 m+1！

```cpp
// tiling.cpp:176
multiTokenNum_ = xShapePtr->GetOriginShape().GetDim(DIM_ONE) - NUM_ONE;  // m = seq_len - 1
```

**2D 输入**（prefill/PD 混部路径）：从 `conv_states` 反推：

```cpp
// tiling.cpp:262
multiTokenNum_ = stateLen_ - (windowSize_ - NUM_ONE);  // m = stateLen - (K-1)
```

**3D 输入强制校验 shape 一致性**（tiling.cpp:256）：

```cpp
multiTokenNum_ != stateLen_ - (windowSize_ - 1)  →  报错
// 即 3D 时 x.shape[1]-1 必须 == conv_states.shape[1]-(K-1)，两处对不上直接拒
```

### 4.3 accepted 决定读缓存偏移：offset = accepted - 1

**为什么读缓存要偏移？** 上一次调用结束时，cache 里存了"上次序列末尾的历史 + 已消费/未消费的 draft"。本次 verify 接受了 a 个 token，意味着**开头 a 个 token 已经"坐实"成为新历史**，读历史窗口时要从 cache 的第 a-1 个之后开始读：

```
offset = accepted - 1        # 需求文档 :267 公式
```

golden（`golden_fused_causal_conv1d_mtp.py:147`）：

```python
offset = num_accepted_tokens[batch_idx].item() - 1 if has_nat else 0
cached_state = conv_states[read_cache_line][: offset + width - 1]   # 注意是 [0, offset+K-1)
padded_input = torch.cat([cached_state, seq_x], dim=0)
padded_input = padded_input[offset:]                                # 消费掉已接受的 a-1 个
```

kernel（`update.h:232-237`，MTP 分支 `cacheMode_=2`）：

```cpp
acceptedTokens_ = numAcceptedTokensGm.GetValue(batchIdx);
dstLocalOffset = (stateLen_ - (acceptedTokens_ + kWindowSizeM2)) * curDim_;  // 目的偏移
srcGMOffset    = readCacheLine_ * convStatesStride0_ + ...;
blockCount     = acceptedTokens_ + kWindowSizeM2;                            // 搬 accepted+K-2 行
```

**accepted 的取值范围**：`0 <= accepted <= m+1`
- `accepted = 0` → prefill 语义（见第五章）
- `1 <= accepted <= m` → 部分接受
- `accepted = m+1` → 满接受（seqLen = m+1 全验证通过）

### 4.4 kernel 消费的是 seqLen 而不是 m

kernel 主循环（`update.h:139`）：

```cpp
seqLen_ = multiTokenNum_ + NUM_ONE;        // 3D: seqLen = m+1（update.h:66）
for (idxS = 0; idxS < seqLen_; idxS++) {   // 对每个 token 做 搬入→写cache→计算→搬出
    ...
}
```

**kernel 不直接读 m**，它读 `seqLen`（3D 时 = m+1；2D 时从 query_start_loc 差分）。m 是 tiling 期从 shape 反推出来的约束，主要用来**校验 + 定 UB 预算**。

### 4.5 本次改动为什么是"放宽 m"

| | 改前 | 改后 |
|---|---|---|
| m 范围 | [0, 7] | **[0, 16]** |
| stateLen 最大 | K-1+7 = 9 | K-1+16 = 18 |
| MAX_DECODE_LEN | 8 | 17 |
| 语义 | 最多 7 个 draft 槽位 | 最多 16 个 draft 槽位，支持更大投机窗口 |

m=16 意味着一次 forward 最多验证 17 个 token（1 个必然 + 16 个 draft），投机吞吐收益上限显著提高。**代价是 stateLen 翻倍，UB buffer 占用翻倍**（第八章详细算）。

### 4.6 golden 怎么验证 MTP

caseData 里 `accepted` 字段就是 per-batch 的接受数，代表点覆盖（`golden_fused_causal_conv1d_mtp.py:535`）：

```
m=0        → [0]                       （纯 prefill）
m>0        → [0, 1, m/4, m/2, 3m/4, m, m+1]
              prefill  单接受  偏小  中间  偏大  满接受  上界
```

7 档覆盖了 accepted 的语义边界：0（prefill）、m+1（满接受上界）、以及中间密度——任何档位漏算（offset 错、blockCount 错）都会让某档 FAIL。

## 五、PD 混部（Prefill-Decode 混合调度）

### 5.1 是什么

**PD 混部**（需求文档 :82 / 原始文档 :82）：**同一个算子调用里，prefill 和 decode 批次共存**，混合调度。

- 传统推理：prefill 阶段（吃整条 prompt）和 decode 阶段（逐 token 生成）分开跑
- PD 混部：一个 batch 里既有"正在吃长 prompt 的请求"（prefill），又有"正在逐 token 生成的请求"（decode）
- 收益：算力不空闲、调度更紧凑；代价是模板要同时支持两种序列语义

### 5.2 怎么区分：num_accepted_tokens 一票两用

```
num_accepted_tokens[b] == 0  →  该 batch 是 prefill：缓存只写最后 K-1 个 token
num_accepted_tokens[b] >= 1  →  该 batch 是 decode：缓存写最后 accepted+K-2 个 token（含 draft）
```

代码：`update.h:232-237`（hasNumAcceptedTokens 分支）、`fn_cutbs.h:294` `GetOffset`。

**两种语义对应的缓存读写差异**：

| | prefill（accepted=0） | decode（accepted>=1） |
|---|---|---|
| offset | stateLen - (K-1)（读最后 K-1 个） | accepted - 1 |
| 读的 cache 范围 | 最后 K-1 个 | [0, accepted+K-2) |
| 写回 cache | 最后 K-1 个 | 最后 accepted+K-2 个 |
| seq_len | 任意长（变长） | 固定 m+1（3D）或 query_start_loc 差分（2D） |

### 5.3 runMode 判定：PD 混部走哪条路径

tiling 阶段判定（`tiling.cpp:101`）：

```cpp
runMode_ = (maxQueryLen_ > MAX_DECODE_LEN || maxQueryLen_ <= 0) ? 0 : 1;
// runMode = 0 → prefill / PD 混部路径（2D x，CUTBS/CUTBSD 模板）
// runMode = 1 → decode 路径（Update 模板）
```

- **maxQueryLen > 17（或 <= 0）→ prefill/PD 混部**：2D 变长 x `[cu_seq_len, D]`，query_start_loc 切 batch，每个 batch 长度任意（这就是 PD 混部的形态：有的 batch 长、有的 batch 短）
- **否则 → decode**：3D x `[B, m+1, D]` 或 2D，seqLen 固定

**为什么 MAX_DECODE_LEN 要改成 17**：m=16 时 3D x 的 seqLen = m+1 = 17，maxQueryLen 必须 ≤ 17 才走 decode。如果 MAX_DECODE_LEN 还是 8，m=16 的调用会被误判成 prefill 路径，3D 输入直接报错（`tiling.cpp:169` 要求 3D 必须 runMode=1）。

### 5.4 PD 混部在 kernel 里的处理

2D 输入下 kernel 逐 batch 从 query_start_loc 推导 seqLen（`update.h:116-118`）：

```cpp
if (isXDimSizeTwo_) {
    seqLen_ = queryStartLocGm.GetValue(batchIdx + 1) - tokenIdx_;
}
```

于是同一个循环里，前一个 batch 可能是 1024 长的 prefill，后一个 batch 可能是 2 长的 decode——**每个 batch 独立算缓存偏移、独立卷积**，互不干扰。

### 5.5 Pangu V2 的 reset 逻辑（conv_mode=1）

Pangu V2 的序列卷积对"新序列开头"有特殊要求：一个序列**开头 K-1-numComputed 个输出要置 0**（因为前面没有真实历史，防止泄漏/错位）：

```
lastResetIdx = max(0, min(K-1 - numComputedTokens[b], seqLen))
idxS < lastResetIdx  →  输出置 0（或置 x，残差模式）
```

代码：`update.h:134-138` + `update.h:425`（置零分支）、`fn_cutbs.h:280` `GetLastResetIdx`、`fn_cutbsd.h:276`。
golden：`golden_fused_causal_conv1d_mtp.py:157-160`（`result[:last_reset_idx] = 0`）。

**golden 验证**：caseData 的 `num_computed` 字段逐 batch 控制，覆盖 numComputed ∈ {0, 1, 2, 大值}——0 触发零初始化、1/2 触发部分 reset、大值不触发。

## 六、APC 前缀缓存

### 6.1 为什么需要

**APC（Automatic Prefix Caching）**：跨调度 chunk 复用 KV/状态缓存。

场景：一次调度只处理一部分 token（一个 chunk），下次调度处理后续 token。如果每个 chunk 都从零开始，历史就丢了。APC 用**block 粒度**管理缓存——每个 block（如 128 个 token）结束时，把 block 边界处的 K-1 个 token 存成一个独立的"prefix cache"行。下次调度直接读对应 block 的缓存行，**跨 chunk 复用，不用重算**。

### 6.2 数据结构：cache_indices 从 1D 变 2D

```
非 APC: cache_indices = [B]                  每个 batch 一行 running cache
APC:    cache_indices = [B, maxNumBlocks]    每个 batch 多行：running cache + 若干 prefix cache
```

kernel 里 APC 分支（`update.h:187-202` `CalRunningCacheRWIdx`）：

```cpp
initialIdx      = initialStateIdxGm.GetValue(batchIdx);            // 从哪个 block 开始读
idxFirst_       = blockIdxFirstScheduledTokenGm.GetValue(batchIdx);
idxLast_        = blockIdxLastScheduledTokenGm.GetValue(batchIdx);
nBlockToFill_   = idxLast_ - idxFirst_;                            // 本次要写几个 prefix block
readCacheLine_  = cacheIndices[batch, initialIdx];                 // 读行
writeRunCacheLine_ = cacheIndices[batch, idxLast_];                // 写行（running cache）
```

### 6.3 block 边界对齐计算

```
seqCompletedOffsetToken = numComputedTokens[b] % blockSize        # 起始 token 在 block 内偏移
seqCompletedOffset      = blockSize - seqCompletedOffsetToken     # 当前 block 还剩几个坑
seqEndOffset            = (seqLen - seqCompletedOffset) % blockSize
lastFullBlockTokenIndex = seqLen - seqEndOffset                   # 最后一个满 block 的起点
```

代码：`update.h:189-195`、`fn_cutbs.h:233-242`、`fn_cutbsd.h:246-255`。
golden：`golden_fused_causal_conv1d_mtp.py:164-170`（APC 分支逐 chunk 写 `conv_states[wcl][-(K-1):]`）。

### 6.4 prefix cache 写入（kernel）

```
for chunk in range(nBlockToFill_):
    boundaryIdx = lastFullBlockTokenIndex - (nBlockToFill_-chunk-1) * blockSize
    writeCacheLine = cache_indices[batch, idxFirst_+chunk]
    conv_states[writeCacheLine][:K-1] = padded_input[boundaryIdx : boundaryIdx+K-1]
```

- 每个 block 存它**边界处**的 K-1 个 token（需求文档 :284"仅需缓存每个 block 的最后两个 token"）
- 特殊情形：`boundaryIdx < K-1` 时（block 边界落在序列开头），prefix cache 要混写"缓存行 + x 行"（`fn_cutbs.h:659` 注释详解）

kernel 代码：`update.h:301` `CopyOutConvStatePreCache` + `:396` `CopyOutXPreCache`（运行中逐 token 写）、`fn_cutbs.h:647-711`、`fn_cutbsd.h:629-694`。

### 6.5 与 MTP 的关系

**两者正交**：
- APC 管"跨调度的缓存复用"（读哪个 block、写哪些 block）
- MTP 管"一次 forward 内的多 token 处理"（读缓存时偏移多少）

同时开启时，读偏移仍是 `accepted - 1`，只是"从哪个 cache 行读"由 APC 的 `initialStateIdx` 决定。

## 七、Kernel 全景：三个模板怎么分工

### 7.1 入口分派（`ai_infra_fused_causal_conv1d.cpp`）

kernel 入口按 TilingKey + dtype + windowSize 三重分派，实例化模板类：

```
TilingKey 0 (CUTBSD) → KernelAiInfraFusedCausalConv1dFnCutbsd<dtype, K>
TilingKey 1 (CUTBS)  → KernelAiInfraFusedCausalConv1dFnCutbs<dtype, K>
TilingKey 2 (Update) → KernelAiInfraFusedCausalConv1dUpdate<dtype, K>
```

- `K` 是**编译期模板参数**（3/4/5/6），kernel 里所有循环上界是常量，全展开
- dtype 是 bf16/fp16，各编译一份（`#if ORIG_DTYPE_X`）

### 7.2 三模板适用场景对比

| 模板 | TilingKey | runMode | 场景 | 计算风格 | stateLen 依赖 |
|---|---|---|---|---|---|
| **Update** | 2 | decode(1) | MTP/短序列 | 递推器，逐 token | 强（convStatesQueue 线性） |
| **CUTBS** | 1 | prefill(0) | dim < 3152 且序列长 | 批量搬 token + 向量乘累加 | 强（cacheQue/cacheBuf 线性） |
| **CUTBSD** | 0 | prefill(0) | dim ≥ 3152 或序列短 | 逐 token 递推 | 弱（不依赖 stateLen） |

> **为什么 prefill 要分两个模板**：dim 大时一核放不下整行，按 token 逐行处理（CUTBSD，token 流水）；dim 小时可以一次搬一批 token 进 UB（CUTBS，ubFactor 个 token 并行算）。两种都保留是因为性能权衡不同。

### 7.3 Update 模板主循环（decode/MTP 主路径）

```
Process（update.h:106）:
  1. CopyInWeight()          # 搬 weight、cast fp32、残差融合 w[K-1]+=1（update.h:155）
  2. for 每个 batch:
       CalRunningCacheRWIdx()    # APC/非 APC 计算读写 cache 行（update.h:179）
       pad slot? → skip         # pad_slot_id 跳过无效 batch（update.h:123）
       CopyInConvState()         # 读 cache（含 MTP offset、零初始化分支）（update.h:214）
       CopyOutConvStateRunCache()/PreCache()  # 写回"本来就是 cache 的部分"（update.h:268/301）
       InitY()                   # 用 K-1 个历史 token 喂入递推器，恢复 y 状态（update.h:325）
       for 每个 token (seqLen=m+1):
           CopyInX()             # 搬入当前 token 并 cast fp32（update.h:354）
           CopyOutXRunCache()    # 逐 token 写回 cache（update.h:380）
           CopyOutXPreCache()    # APC：逐 token 写 prefix cache（update.h:396）
           ComputeAndUpdate()    # 递推器：输出 + 滚动更新（update.h:420）
           CopyOutY()            # cast 回 dtype、写回 y（inplace 时写回 x）（update.h:473）
```

**为什么先写 cache 再计算**：cache 里要存的是"原始输入 token"，不是卷积结果。所以 `CopyOutXRunCache` 在 `ComputeAndUpdate` 之前，搬进来的 x 先原样落缓存，再进递推器。

**分核方式**（tiling 算好，kernel 按 blockIdx 取）：核先按 batch 切（coreBatchAct），batch 内再按 dim 切（coreDimAct），每个核处理 `baseBatch × curDim` 的一块。

### 7.4 CUTBS 模板的批量计算

与 Update 的逐 token 递推不同，CUTBS 一次搬 **ubFactor 个 token + K-1 个历史**进 UB，然后**向量化批量卷积**（`fn_cutbs.h:494` Compute）：

```
Mul(yFp32, xFp32[rowId-(K-1)], weightFp32, K*curBaseDim)   # 广播乘：yFp32[k] = x[t-K+1]·w[k]
for k in 1..K-2: Add(yFp32, yFp32, yFp32[k*curBaseDim])     # 累加
Add(xFp32[rowId-(K-1)], yFp32, yFp32[(K-1)*curBaseDim])     # 加上 w'[K-1] 项（含残差）
```

**输出复用输入槽**：结果直接写回 `xFp32[rowId-(K-1)]`（输入 buffer 的对应位置），省一块输出 buffer。

### 7.5 CUTBSD 模板：逐 token + 跨核恢复

dim 大、一次只能放一行，逐 token 处理。两个特殊函数：

- `InitY`（fn_cutbsd.h:321）：batch 首 token，从 cache 读 K-1 个历史喂入递推器
- `RestoreY`（fn_cutbsd.h:366）：**核从序列中间启动时**（tiling 按 token 切核，核边界不在 batch 边界上），从 x 里回读前 K-1 个已算 token 重建递推状态——因为 y 状态在 UB 里，跨核不共享

### 7.6 三个模板的共性（都是因果卷积）

无论哪个模板，数学核心都是同一个递推/累加；差异只在**数据搬移的粒度**（逐 token vs 批量）和**缓存恢复的时机**（batch 首 vs 核首）。理解这点，读任何模板都不怕。

## 八、Tiling：常量、校验与 UB 预算

### 8.1 关键常量（`ai_infra_fused_causal_conv1d_tiling.h:80-97`）

| 常量 | 值 | 含义 |
|---|---|---|
| `MIN_WINDOWSIZE` / `MAX_WINDOWSIZE` | 3 / 6 | 卷积核 K 范围 |
| `MAX_DECODE_LEN` | **17**（本次 8→17） | runMode 判定阈值，= MAX_M + 1 |
| `MAX_M` | **16**（本次 7→16） | m 上限 |
| `MIN_DRAFT_TOKENS` / `MAX_DRAFT_TOKENS` | 0 / 16 | maxDraftTokens 合法范围 |
| `DEFAULT_MAX_DRAFT_TOKENS` | 7 | 缺省值（向后兼容） |
| `MAX_DIM_CUTBS` | 512 | CUTBS 内 baseDim 上限 |
| `MAX_DIM_CUTBSD` | 3152 | CUTBS/CUTBSD 切换阈值 |
| `MIN_DIM` / `MAX_DIM` | 64 / 16384 | dim 范围（须 %16==0） |

### 8.2 三层校验体系（本次新增第二、三层）

```
层1（shape 硬约束）:  m = stateLen-(K-1)（2D）或 x.shape[1]-1（3D）∈ [0, MAX_M]
                      tiling.cpp:264（2D 推导后校验）/ tiling.cpp:179（3D 直接校验）
层2（attr 范围）:     maxDraftTokens ∈ [0, 16]，缺省/未传 → 7
                      tiling.cpp:133-148（防御读 + 范围校验）
层3（m 与 attr 关系）:  m ≤ maxDraftTokens，否则拒绝
                      tiling.cpp:269-274
```

**为什么需要层3**：maxDraftTokens 是"UB 按它分配的上限"，如果实际 m 超过它，UB 预算按 maxDT 算就会**溢出**。所以 m > maxDT 的调用直接拒绝（`multiTokenNum(%ld) ... must not exceed max_draft_tokens(%ld)`）。

### 8.3 UB 预算公式（三模板各自算）

**Update（decode）**（tiling.cpp:612-627）：

```
spaceWithDim = 2·dtypeSize        # xQueue 双缓冲
             + K·4                # weightQueue (fp32)
             + stateLen·dtypeSize # convStatesQueue ← 随 m 线性增长！
             + dtypeSize          # outputQueue
             + K·4                # yBuf (fp32)
             + 4                  # xBuf (fp32)
maxDim = (ubSize - UB_RESERVED) / spaceWithDim / 16 · 16
```

**CUTBS（prefill 小 dim）**（tiling.cpp:586-600）：

```
cacheQue = 2 · stateLen · dtypeSize · 512     # 双缓冲，← 随 m 线性增长！
cacheBuf =     stateLen · dtypeSize · 512     # ← 随 m 线性增长！
ubFactor = (ubSize - 固定部分) / (2·dtypeSize + dtypeSize + 4·512)  # 每轮处理的 token 数
```

**CUTBSD（prefill 大 dim）**（tiling.cpp:550-562）：`spaceWithUbfactor` **不含 stateLen** —— buffer 与 m 无关，本次改动完全不受影响。

**关键**：UB 预算全部从 tiling data 的 `stateLen` 动态读，m 变大 → stateLen 变大 → maxDim/ubFactor 自动收缩，**保证不溢出，代价是性能**（见 §8.4）。

### 8.4 m 增大对性能的影响

| 模板 | buffer 增长 | 性能代价 |
|---|---|---|
| CUTBS | cacheQue+cacheBuf 与 stateLen 成正比 | ubFactor 28→24，循环次数 +18% |
| Update | convStatesQueue 与 stateLen 成正比 | maxDim 减小约 25%，dim 核切分增加 |
| CUTBSD | 无 | **不受影响** |

### 8.5 maxDraftTokens 与 UB 的关系（本次新机制）

```
effectiveStateLen = max(stateLen, maxDraftTokens + K - 1)     # tiling.cpp:276-278
```

- **stateLen**（实际 shape）决定"要算多少数据"
- **maxDraftTokens + K - 1** 决定"UB 按多大分配"

取 max 后，UB 预算**至少按 maxDraftTokens 分配**。这样：

- **ACLGraph capture/replay 友好**：capture 期 maxDraftTokens 固定 → UB 分配固定 → replay 时 m 在 [0, maxDT] 内变化**不触发动态重 tiling**
- **向后兼容**：缺省 maxDT=7 时，effectiveStateLen = max(stateLen, 9)，m≤7 的旧调用 UB 分配与改动前完全一致（§9.4 兼容性）

|---|---|---|---|
| max_re_ratio | max(\|got-ref\| / max(\|ref\|, 1e-12)) | ≤ 5 | ≤ 10 |
| avg_re_ratio | mean(同上) | ≤ 1.5 | ≤ 2 |
| rms_ratio | sqrt(mean(ratio²)) | ≤ 1.5 | ≤ 2 |

每行输出全指标 + 余量（`max_re=... (thr 5, margin +...)`），PASS/FAIL 都打，一眼看是稳过还是擦边。

**两份输出都判**：y（卷积结果）+ conv_states（写回缓存）。cache 写错不反映在 y 上，只比 y 是常见 false-pass 来源（§3.3）。

### 10.4 只影响 tiling/UB 的参数怎么验证（E/F/G 三层）

maxDraftTokens 是**纯 tiling 参数**——它只决定 UB 怎么分配，不参与卷积数学计算。纯数学 oracle 感知不到它（传任何值输出都一样），所以数值层验证无效。这类参数拆三层验证：

```
层1（合法值域全覆盖）:  F 层，maxDT 全 17 值 × m{0, maxDT}
                        —— m=maxDT 恰在层3 合法边界，每个 maxDT 值都测
层2（缺省链路）:        E 层，不传（None）vs 显式传，两路输出必须一致
                        —— 验证 schema 默认值 7 + binding value_or(7) 生效
层3（非法拦截）:        G 层，expect_fail 用例
                        —— 自洽阶段 SKIP（oracle 不拦截、数学无意义），
                           上板阶段断言调用被拒 → 验证 tiling 层2/层3 校验真实生效
```

**注意缺省参数的硬上限**：缺省 7 只对"实际值 ≤ 7"的调用合法（m>7 时缺省调用会被层3 拒绝，因为 maxDT=7 < m）。所以 E 层 m 限 [0,7]。

### 10.5 可证伪设计（防止假 PASS）

- **双 oracle 独立实现**：一条路径照抄 kernel 逻辑 = 永远自洽，等于没测；两条独立路径互比才能暴露任一方错误
- **边界密集**：CUTBS/CUTBSD 切换点 3152 两侧（3136/3152/3168）、accepted 7 档、m=maxDT 边界、K 双值
- **阴性对照**：G 层非法用例 + `--full` 模式 npu 拒绝断言
- **大 D + 大 m**：D=16384 × m=16 覆盖 UB 最紧张场景

### 10.6 待 binding 落地后

`--full` 模式调 `torch.ops.custom.npu_ai_infra_fused_causal_conv1d(..., maxDraftTokens=...)`，npu 输出 vs oracle ratio 比对（E 层不传 kwarg；其余层传 `max(7, m)`；G 层断言被拒）。

## 十二、易混点 Q&A

### Q1: m 和 num_accepted_tokens 什么关系？

- m = 槽位上限（shape 决定，编译/调度期固定）：一次 forward 最多几个 draft
- accepted = 实际接受数（运行时 per-batch）：本次真的接受几个
- 约束：`0 ≤ accepted ≤ m+1`。accepted=m+1 是满接受

### Q2: maxDraftTokens 和 m 什么关系？

- m = 本次调用的实际投机数（shape 隐式）
- maxDraftTokens = UB 分配上限（attr 显式，默认 7）
- 约束：**m ≤ maxDraftTokens**（层3 拦截），否则 UB 按 maxDT 算会溢出
- UB 按 `effectiveStateLen = max(stateLen, maxDT+K-1)` 分配

### Q3: run_mode 和 num_accepted_tokens 什么关系？

两者独立。run_mode 由 max_query_len 判定选**模板**（CUTBS/CUTBSD vs Update）；num_accepted_tokens 决定**单个 batch 是 prefill（0）还是 decode（≥1）**，在 kernel 里逐 batch 生效。PD 混部 = run_mode=0 的调用里同时出现两种 batch。

### Q4: 2D 和 3D 输入什么时候用？

| 输入 | 场景 | m 从哪来 |
|---|---|---|
| 3D `[B, m+1, D]` | decode 主路径（seqLen 固定 m+1） | `x.shape[1] - 1` |
| 2D `[cu_seq_len, D]` | prefill / PD 混部（变长） | `stateLen - (K-1)` 反推 |

### Q5: 为什么改了 MAX_DECODE_LEN？

m=16 时 3D x 的 seqLen=17。MAX_DECODE_LEN 是 prefill/decode 判定阈值，不改成 17 的话 m=16 的调用会被误判 prefill，3D 输入直接报错。

### Q6: kernel 要不要改？

**不用改**。kernel 所有 buffer 大小都从 tiling data 的 stateLen/multiTokenNum 动态分配（`update.h:96-104` 等），m 放大后 tiling 自动给更大预算，kernel 零改动零回归。这是本次需求"kernel 侧无需修改"的机制保证。

### Q7: 大 D + 大 m 会 UB 溢出吗？

**不会**（tiling 预算自适应收缩），但性能会劣化：D=16384 × m=16 时 Update 路径 maxDim 减小、dim 核切分增加。最坏情况需上板 msprof 验证（R1 风险）。

### Q8: 为什么 golden 要比 conv_states？

缓存写错不反映在 y 上（y 只依赖读到的历史，不依赖"写回的缓存"）。两份输出都比，cache 错写才不会被漏检。golden 自洽已覆盖，上板 --full 也两份都比。

### Q9: maxDraftTokens 传大了有代价吗？

UB 按 maxDT 分配，传 16 但实际 m=7 时 cacheQue/cacheBuf 浪费约一半。默认 7（向后兼容），建议按实际 draft 模型能力设置（draft k=8 就传 8）。ACLGraph 场景下固定 maxDT 换"m 变化不重 tiling"，整体收益大于浪费。

### Q10: A5 要不要同步改？

本次不涉及（需求明确 A2/A3 推理）。上游 ops-transformer_AI 仓 arch35 路径也是 MAX_M=7，后续要扩展 A5 再同步。
